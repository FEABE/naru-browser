# Naru 독립 브라우저 통합 검증 체크리스트

작성일: 2026-10-16. 최근 갱신일: 2026-10-20. 목표는 ego lite 수준으로 사람이 일상 탐색을 하는 동안 AI가 별도 공간에서 CLI로 작업하는 Naru 독립 브라우저를 완성하는 것이다. 기본 개발판의 완성으로 목표를 낮추지 않는다. 같은 구현을 Preseller에 내장하는 일은 그다음 단계다. 현재 후보는 v18이며 최신 네이티브 확인을 바로 아래에 기록했다. 뒤의 v17과 e2e-v14 실행 정보는 이전 실행의 이력으로 유지한다. 서로 다른 바이너리의 통과를 합산해 전체 완성을 선언하지 않는다.

참고 기준은 [2026-10-11 실제 앱 비교](browser-comparison-2026-10-11.md)다. 당시 ego lite `0.5.1.13`에서 별도 AI 공간, 사용자 선택 유지, 작업 표시, 로컬 페이지 클릭과 입력을 관찰했다. Aside에서는 새 탭, 세로 탭, 북마크, 통합 검색과 중지 UI를 관찰했다. 당시 확인하지 않은 로그인, 모든 중지 경합, 전체 웹 호환성과 메모리 우열을 동등성 기준에 추가하지 않는다. 아래 항목은 그 관찰과 Naru의 제품 목표를 합친 지원 범위이며, 최신 ego lite의 전체 기능 목록을 복제한 표가 아니다.

## 2026-10-20 대상 스크롤 소스와 다음 실행 목록

현재 소스에 `scroll TAB REF DX DY`와 [대상 스크롤 계약](targeted-scroll.md)을 추가했다. 앱 번들은 아직 v18이며 새 기능은 빌드 전이다. 신규 Rust 단위 검사 6개와 모의 DOM 검사 9개 통과는 아래 실제 CEF 여정의 통과가 아니다.

전용 러너 `tests/scroll_target_smoke.py`와 `tests/fixtures/scroll-target.html`은 다음 통합 빌드의 격리 프로필에서 실행한다. 현재 판정은 모두 pending이다.

1. 메인 목록, 열린 Shadow DOM 목록, 동일 출처 프레임 목록에서 요청한 상대 이동량과 다시 읽은 좌표가 일치하는지 확인한다.
2. 실제 child session이 있는 OOPIF의 목록과 프레임 문서를 지정한다. 원래 포커스와 부모 문서 및 다른 목록의 좌표, 사용자 공간과 선택 탭이 유지되는지 확인한다.
3. `read-page`가 반환한 여러 문서의 참조를 같은 읽기 결과에서 각각 실행한다. 새 읽기 전의 오래된 참조와 handoff 후의 이전 revision은 거절돼야 한다.
4. 요소를 다른 문서로 옮긴 뒤 옛 참조를 거절하고, 기존 `scroll TAB DX DY`의 메인 문서 이동도 확인한다. 작업 탭과 서버를 정리한 결과를 남긴다.

커밋 `9d32ee4`를 release로 빌드했다. 앱 SHA-256은 `0d8d2c5bd1db019768c2eda745b0e78d7177cb6fad90e777aac40a8e165fa450`, CLI는 `79e398f1a54b8254579d916adc242e1308964a596570d85f939f621bde0d0607`이다. 소스 manifest와 빌드, 같은 바이너리의 실행 및 정리를 `artifacts/e2e-v18-download-restart-20261020/`에 기록했다.

09번의 수동 재요청 여정은 실제 앱에서 확인했다. 실패 표시 후 서버를 복구하고 다시 받기, 새 저장창 취소, 취소된 새 항목에서 다시 받기, 새 이름 저장과 131,072바이트 및 원본 해시 일치를 확인했다. AI 탭의 취소 항목을 사용자 공간에서 다시 받아도 선택과 active revision이 유지됐고 handoff는 저장 대기를 취소했다. 최종 다운로드와 저장, 권한 대기는 0이며 검증 AI 작업은 finished다. [상세 실행](native-e2e-2026-10-20.md#v18-수동-다시-받기)을 따른다.

09번 전체는 pending이다. 권한 UI와 Finder 대상 선택, 응답 없는 재요청 timeout 등 남은 범위를 완료로 올리지 않는다. 다른 13개 여정도 v18에서 다시 확인한 결과가 없으며 v17의 통과를 옮기지 않는다. 전체 회귀 묶음은 실행하지 않았다.

## 개발과 검증 순서

남은 기능을 지원 범위 안에서 먼저 구현한다. 기능을 조금 바꿀 때마다 전체 Rust, 모의 DOM, CEF 회귀 묶음을 반복하지 않는다. 구현에 필요한 좁은 확인과 통합 시점의 필수 컴파일을 구분하고, 통합 빌드가 준비되면 아래 14개 사용 여정을 한 앱 바이너리로 검증한다. 기존 스크립트는 해당 여정에 필요한 부분만 활용한다.

결함을 고친 뒤에는 실패한 여정과 영향을 받는 여정을 다시 확인한다. 다른 바이너리의 통과 결과를 새 바이너리의 통과로 옮기지 않는다. 최종 완료를 판단할 빌드가 정해지면 아래 목록을 그 빌드 기준으로 한 번 정리한다. 새 빌드 때문에 검증을 시작하지 못하면 `blocked`로 남기고 같은 승인 질문이나 전체 검사를 반복하지 않는다.

DevTools 전송 변경 후에는 04의 read와 screenshot, 06과 07의 입력, 13의 취소와 복구를 같은 후보에서 확인한다. raw 응답의 루트 구분, ID 고갈과 잘못된 Browser의 응답 거절은 별도 소스 경계 검사이며 실제 UI 성공을 대신하지 않는다. `frames TAB`의 [하위 연결과 메타데이터 수집](devtools-routing.md)에 이어 `read-frame TAB FRAME`의 [한 프레임 본문 읽기](frame-read.md)를 구현했다. 08에서는 목록, 본문, 입력 7개와 부모 상태·좌표·가림 검사를 구분해 확인한다. 포인터는 축 정렬 변환을 지원하며 회전·perspective·pinch 등 지원 밖 기하의 거절도 확인한다.

입력 여정 06의 재현 준비는 `tests/native_click_smoke.py`, `tests/native_fill_smoke.py`, `tests/contenteditable_smoke.py`, `tests/insert_text_smoke.py`에 있고 07은 `tests/native_press_smoke.py`에 있다. 06과 07의 스크립트는 e2e-v14에서 실행했다. 구문 확인이나 테스트 항목 추가만으로 pass를 기록하지 않는다.

행마다 같은 실행 ID와 앱 SHA-256, 시작과 종료 상태, 실제 CLI 응답이나 화면, 실패 원인, 정리 결과를 근거에 연결한다. 비밀번호, 인증 코드, 쿠키, 토큰과 개인 페이지 본문을 로그에 남기지 않는다. 원본 실패 증거는 지우지 않고 수정 후 확인을 별도 기록한다. `pass`에는 예정된 검사나 이전 빌드의 성공을 넣지 않는다.

- `pending`: 아직 실행하지 않았거나 같은 최종 빌드의 확인이 남음.
- `pass`: 해당 행의 완료 조건을 같은 앱에서 확인하고 근거를 남김.
- `fail`: 실행했지만 완료 조건을 충족하지 못함. 재현 동작과 실제 영향을 기록함.
- `blocked`: 실행에 필요한 환경이나 직접 사용자 조작이 없어 확인하지 못함. 원인과 재개 조건을 기록함.

## 실행 범위

**계정과 외부 폼 제출 없이 진행:** 자체 localhost fixture의 읽기, 입력, 취소, 페이지 이동과 파일 처리, 네이티브 브라우저 UI, 공개 웹페이지의 읽기와 링크 이동이다. fixture의 폼은 외부로 전송하지 않으며 필요한 경우 로컬 이벤트만 관찰한다. 외부 공개 사이트는 네이버 메인(`https://www.naver.com/`)과 Wikipedia 공개 문서(`https://en.wikipedia.org/wiki/Web_browser`)의 표시, 읽기, 링크, 뒤로 가기, 페이지 찾기로 한정한다. 검색어는 일반 검증 문구를 쓰고 비공개 정보는 넣지 않는다. 접근 제한이나 CAPTCHA가 나오면 우회하지 않고 해당 단계의 `blocked` 근거를 남긴다.

**사용자가 직접 진행:** 로그인할 대표 서비스와 계정을 선택하고 로그인, 인증 코드, CAPTCHA, macOS 보안 승인이 필요한 경우 직접 조작한다. 에이전트가 비밀번호를 받거나 입력하지 않는다. 로그인 후에는 사용자가 정한 페이지에서 상태 유지와 읽기만 확인한다. 외부 폼 제출, 메시지 발송, 구매, 계정 설정 변경, 외부 파일 업로드는 이 체크리스트에 포함하지 않는다. 서비스가 정해지지 않았으면 로그인 지원을 검증했다고 표시하지 않는다. IME는 실제 한글 조합 입력이 필요하며 붙여넣기로 대체하지 않는다.

기록 전체 삭제와 손상 복구는 사용자 이력이 없는 기존 검증 프로필에서만 수행한다. 적합한 프로필이 없으면 이 단계는 `blocked`로 남기고 사용자 기록을 지우지 않는다. 다운로드와 파일 선택은 전용 임시 경로와 자체 만든 무해한 파일만 사용한다. 렌더러 종료는 자체 검증 탭만 영향을 받는 프로세스를 식별한 경우에만 수행한다. 사용자 탭과 프로세스를 공유하거나 대상을 확정할 수 없으면 강제 종료하지 않는다.

## 06·07번 입력 준비와 해제의 실행 목록

아래는 [임시 포커스 준비](focus-input.md)와 일반 입력칸의 이벤트 관찰을 위한 실행 전 목록이다. 기능 소스와 컴파일 확인을 실제 입력 성공으로 기록하지 않는다.

1. 사용자 공간의 주소 초안에 포커스를 둔 채 배경 작업에서 press·fill·insert를 실행한다. 원 Browser와 정확한 session의 enable ACK, 새 준비, 단일 입력 시도, disable ACK, 읽기 전용 사후 확인 순서를 기록하고 사용자 공간·선택·네이티브 입력 포커스가 유지되는지 확인한다. 키의 단일 시도는 기존 keyDown·keyUp 한 쌍을 뜻한다.
2. 처음 페이지 포커스를 받을 때 다른 요소로 이동하는 동기 핸들러를 만든다. 준비 단계의 실제 거절과 엔진 요청 수를 확인한다. 이어 timer·rAF로 준비 뒤에 포커스를 바꾸는 경우도 실행하고 잘못 입력된 대상, mismatch·unconfirmed와 실제 영향을 구분한다. 첫 조건의 성공으로 두 번째 경합까지 해결했다고 기록하지 않는다.
3. 일반 입력칸과 textarea에서 trusted beforeinput·input이 원 대상과 다른 대상으로 전달되는 경우를 확인한다. 원 대상이 이미 요청값과 같더라도 다른 대상 관찰이 있으면 성공하면 안 된다. beforeinput 취소, 빈 값, 여러 줄, maxlength, Shadow DOM의 retargeting, 관찰 만료와 같은 시점의 사람 입력을 구분한다. receipt를 사람 입력과 AI 입력의 완전한 식별자로 해석하지 않는다.
4. enable 응답 전, 입력 전송 후, disable 응답 전의 취소·인계·시간 초과와 탐색을 각각 확인한다. 원 session의 해제는 요청 token이나 문서 세대가 바뀌어도 이어져야 한다. 해제 미확정 탭의 새 페이지 조작은 거절하고 다른 탭의 작업은 유지한다. 지연 응답이 입력을 재전송하거나 성공 응답을 두 번 만들면 실패다. 입력 중 탭을 닫았을 때 앱이 종료 오류 없이 남은 사용자 탭을 유지하는지도 확인한다.
5. disable의 blur·visibility 핸들러가 값이나 문서를 바꾸는 경우, 해제 후 결과 확인이 이를 반영하는지 확인한다. 해제 실패·ACK 누락·session 종료를 실제로 구분하고 미확정 상태를 정리 완료로 기록하지 않는다. 페이지 가시성 변화와 실제 AppKit 선택 변화도 별도로 관찰한다.
6. 실제 child session이 있는 OOPIF에서도 같은 흐름을 확인한다. root enable ACK만으로 모든 child가 준비됐다고 판단하지 않는다. 해당 child session의 실제 detach는 session-destroyed 오류로 종료하고 기존 frame 정리를 이어야 하며, 다른 subtree의 detach를 원 lease의 해제로 오인하면 안 된다. renderer reset 완료 ACK와도 구분한다. 14번 지속 사용에서 탭별 임시 상태와 전체 상한, 이벤트 관찰자의 소비·단발 만료, session 정리 후 자원 회수를 함께 확인한다.

## 08번 프레임 여정의 실행 목록

아래는 실행 목록이다. 실행한 결과는 08번 행의 근거 칸에 적었다. `frames` 성공을 frame-local 본문 읽기나 입력 성공으로 계산하지 않는다. 모든 명령은 기존 사용자 탭과 선택을 기록한 뒤 자체 작업·fixture에서 수행한다.

1. 메인 문서와 같은 출처의 중첩 iframe을 만든다. `task run ID REV frames TAB`에서 부모 관계와 고유 frame ID, root session을 확인한다. 기존 read·screenshot도 이어 실행해 응답이 섞이지 않는지 확인한다.
2. 다른 site의 자체 iframe과 그 안의 iframe을 포함한다. 실제로 child session이 생성됐는지 확인하고 root·child 결과의 부모 연결과 중복 없는 합계를 비교한다. 출처가 다르다는 이유만으로 OOPIF라고 판정하지 않는다. 같은 session의 cross-origin도 구분한다.
3. 같은 페이지에서 frames를 두 번 조회한다. 선택한 사용자 공간·탭·주소 초안이 유지되고, 재사용한 연결에 중복 등록이나 프레임 누락이 없는지 확인한다.
4. 프레임 추가·삭제, child 탐색과 process swap을 수집 중과 완료 후에 각각 수행한다. 수집 중 관찰된 변경은 FRAME_CHANGED여야 하며 다음 안정된 조회가 이전 행을 재사용하지 않아야 한다. 단순 경과시간만으로 경합이 재현됐다고 기록하지 않는다.
5. 늦는 수집을 task handoff·중지·타임아웃과 탭 종료로 끝낸다. 기존 revision의 응답을 성공으로 받지 않으며 다른 작업의 캡처나 입력 요청을 소비하지 않는지 확인한다. 해제 ACK가 없으면 정리 성공으로 표시하지 않는다.
6. 연결 16개·깊이 8의 경계와 초과 fixture, frame 128개·트리 깊이 32·긴 metadata를 확인한다. 연결 초과는 FRAME_LIMIT과 추적 중지, 메타데이터 예산 초과는 truncated로 구별한다. 자체 fixture가 실제 한도에 도달했는지도 함께 기록한다.
7. 수집과 자체 작업 종료를 반복한 뒤 E2E 14의 요청·프로세스·메모리 관측에 연결한다. 성공 시 재사용하는 registry와 요청 뒤 해제하는 메타데이터를 구분하며 등록 수 제한만으로 Chromium 전체 RAM이 회수됐다고 판단하지 않는다.

8. 메인·같은 출처·다른 출처의 각 문서와 열린 shadow에 서로 다른 표식을 둔다. `task run ID REV read-frame TAB FRAME`의 URL·본문·요소 정보가 선택 문서와 열린 shadow만 포함하고 자식 iframe 본문은 중복 포함하지 않는지 확인한다. iframe 메타데이터는 not-inspected이고 interactive의 ref는 해당 snapshot에 묶여야 한다. focusedRef는 같은 결과의 ref이거나 null이고 supportedActions는 scroll을 포함한 8개, pointerActionsSupported는 true, atomic은 false여야 한다. 부모에 가려진 프레임의 읽기를 화면에서 보이는 증거로 계산하지 않는다.
9. 같은 frame을 반복해 읽으며 고정 world가 재사용되고 Runtime disable→enable 때 기존 context 이벤트가 다시 관찰되는지 확인한다. source의 uniqueContextId 사용과 실제 대상 문서 표식을 함께 확인하고 사용자 공간·선택·주소 초안을 유지한다. Runtime disable ACK를 world 메모리 해제나 평가 취소의 증거로 기록하지 않는다.
10. 읽기 수명 중 context 파괴·cleared, frame 탐색·detach·process swap을 실제로 발생시킨다. numeric ID가 같더라도 다른 unique context로 이어 읽으면 실패다. 현재 목록에서 사라진 frame ID는 FRAME_NOT_FOUND, 관련 변경 중 읽기는 오류여야 하며 다른 문서의 본문을 성공으로 반환하면 안 된다. 경합을 실제로 재현하지 못한 경우 pending 또는 blocked로 남긴다.
11. root와 child 각각의 지연 읽기를 인계·중지·요청 취소로 끝낸다. root Runtime disable과 auto-attach 해제의 각 ACK, child detach, 늦은 결과 거절을 구분해 기록한다. cleanup 실패·대기 중 새 discovery를 막는지 확인하고 본문 결과만 받았다고 성공 처리하지 않는다.
12. 한 프레임의 본문 12,000자·요소 120개·옵션 전체 240개와 응답 2MiB의 상한, 로딩 중 문서의 PAGE_LOADING을 확인한다. 반복 읽기 후 최신 native 묶음 하나(단일 read-frame 1개, read-page 최대 16개 문서·전체 120 refs)와 약한 DOM 참조, 요청 상태 회수를 E2E 14에 연결한다. 이전 world의 ref 메타데이터는 즉시 모두 지워지지 않으며 Runtime disable, world 재사용과 registry 상한만으로 전체 RAM 절감을 주장하지 않는다.

13. root·같은 프로세스의 교차 출처 문서·실제 child session이 있는 OOPIF 각각에서 반환된 ref로 fill·insert·press·check·select를 연결한다. 입력칸 전체 치환, 현재 선택 치환, 편집기 이벤트, 키다운 대상, checkbox와 단일 select의 실제 상태를 확인한다. 원 session·unique context의 준비와 사후 확인, Runtime disable ACK 뒤 단일 응답을 기록한다. 이어 frame ref의 hover·click은 정확한 root session과 좌표로 전송되어야 하며 DOM 사후 확인은 원 child context를 사용해야 한다.
14. 프레임의 부모와 그 조상에 hidden, display:none, inert, 제거 및 탐색을 적용한다. 부모 world의 실제 frame owner가 현재 문서에 속하고 연결됐는지 확인하며 입력 전에 거절해야 한다. 열린 shadow 안의 iframe, 중첩 부모, 같은 session의 부모도 포함한다. iframe이 다른 요소에 가려진 경우 포인터 후보가 해당 부모의 hit-test에서 제거되는지 확인한다. 키·텍스트 입력의 부모 상태 검사는 포인터 가림 보장과 구분한다.
15. 같은 프레임 또는 다른 프레임을 새 read-frame으로 읽은 뒤 이전 ref를 재사용한다. 새 읽기가 접수되어 시작한 뒤 실패한 경우에도 이전 native 묶음은 유효하지 않아야 한다. 시작 전 TAB_BUSY나 준비 상태 거절은 기존 묶음을 교체하지 않는 경계와 구분한다. 문서·context 교체, process swap, 작업 handoff/resume과 취소 후 참조를 자동으로 새 문서에 적용하지 않는지 확인한다. 다른 ref를 직접 조합하거나 prefix를 바꾸면 거절해야 한다.
16. 부모 resolve 요청 중, inspect 후 release ACK 전, 입력 배치 사이와 결과 정리 중에 취소한다. root objectGroup 해제·Runtime disable·autoAttach 해제는 각각 ACK를 확인하고 child session detach도 구분한다. 늦은 DOM.resolveNode 결과나 예외 객체가 남지 않는지 관측하며 정리 미확정을 성공으로 처리하지 않는다. 다른 작업의 요청은 그대로 유지해야 한다.
17. 입력 준비 뒤 지연 focus 핸들러로 다른 frame·요소에 포커스를 옮긴다. 엔진 ACK와 별개로 실제 어느 요소가 바뀌었는지 기록하고 mismatch·unconfirmed·outcomeUnknown을 구분한다. 원 context 검증만으로 잘못된 입력이 예방됐다고 기록하지 않는다. 반복 프레임 읽기와 입력 뒤 약한 참조, 단발 관찰자와 remote object의 누적 여부를 E2E 14에서 확인한다.

회전·skew·perspective·pinch 등 지원 밖 좌표 변환은 아직 구현 전이다. read-page의 전체 예산과 여러 문서 참조는 소스에 연결했으며 아래 추가 여정도 같은 바이너리에서 확인한다. 현재 지원하는 축 정렬 기하를 같은 최종 바이너리에서 실제 입력 여정으로 확인한다. 읽기와 7개 입력의 소스 구현만으로 08번 여정을 완료 처리하지 않는다.

18. same-process iframe과 실제 OOPIF를 각각 2단계 이상 중첩한다. border·padding·양수 scale과 CSS zoom, 열린 Shadow DOM 안의 owner, 부분 viewport 노출과 부모 overlay를 조합한다. leaf의 clip에서 만든 최대 9개 후보가 모든 부모의 content·viewport·hit-test를 통과하고 선택한 root point가 해당 원 요소에 도달하는지 실제 이벤트로 확인한다. 후보 생성은 최초와 스크롤 뒤 합계 최대 18개이며 부모별 hit-test 횟수와 구분한다.
19. 큰 iframe 안에서 viewport 밖의 요소를 선택한다. 최초 가시 후보가 없으면 leaf scrollIntoView를 한 번 요청한 뒤 전체 geometry를 다시 수집해야 한다. OOPIF 조상 스크롤의 비동기 완료 전에는 입력을 보장하지 않으며 보이지 않으면 오류로 끝낸다. frame 포인터의 mouseMoved는 root로 한 번, hover의 press/release는 0회, click은 사후 검사를 통과한 경우에만 각 1회여야 한다.
20. mouseMoved에 반응해 target 또는 부모를 이동·숨김·가림·교체하고 frame 탐색을 발생시킨다. 원 local point와 최종 root point, backend owner와 unique context의 재검사가 실패하면 click을 추가 전송하지 않아야 한다. 후보를 다시 고르거나 스크롤·입력을 반복하지 않는다. 회전, skew, perspective, SVG 조상, motion path, pinch/visualViewport offset은 지원하지 않는 기하로 거절하며 정상 포인터 성공으로 계산하지 않는다. 입력 접수 뒤 페이지 효과와 순차 검사 사이 경합도 기록한다.

## 현재 증거와 아직 없는 증거

read-page 통합 읽기는 08번 여정에 다음 항목을 추가해 같은 바이너리로 확인한다.

1. root·같은 출처·같은 session의 다른 출처·실제 OOPIF와 열린 Shadow DOM의 고유 표식이 documents에 각각 한 번 포함되는지 확인한다. 루트 우선 너비 순서와 문서별 로컬 순서를 구분하며 자식 본문 중복을 허용하지 않는다.
2. 두 개 이상 큰 문서에서 전체 본문 12,000 UTF-16 단위, 요소 120개, 순회 10,000회, 열린 root 64개, 옵션 240개와 로컬 iframe metadata 16개의 공유 한도를 확인한다. used+remaining=limit, 0 예산의 순회 제한, emoji 경계의 유효 문자열, 17번째 문서의 DOCUMENT_LIMIT 및 예산 소진의 READ_BUDGET을 확인한다.
3. 같은 묶음의 서로 다른 두 frame ref로 후속 입력을 실행한다. 접수된 새 read-frame·read-page 뒤 이전 묶음 전체가 만료되는지, 읽기를 시작하기 전 TAB_BUSY 거절은 기존 묶음을 바꾸지 않는지 구분한다. 다른 문서의 ref 접두사를 합성하면 거절해야 한다.
4. 본문 준비 전 로딩 중인 child는 PAGE_LOADING으로 unread에 남고 다음 문서는 이어 읽는지 확인한다. 이미 수집한 context 교체·탐색·소유권 변경과 정리 실패에서는 전체 오류이며 부분 ref를 반환하지 않아야 한다.
5. password 값이 없고 각 문서의 focusedRef가 해당 문서의 반환 refs에만 포함되는지 확인한다. 화면에 숨긴 부모의 내용 조회를 실제 화면 가시성으로 해석하지 않는다. 문서별 본문 합계와 최종 응답의 2MiB 제한도 확인한다.
6. 사용자 공간·탭 선택·주소 초안을 유지하며 취소·인계·늦은 응답 뒤 참조와 요청 상태를 회수하는지 확인한다. 14번 지속 사용에서 최신 native 묶음 상한과 각 world의 약한 메타데이터 잔류를 구분해 측정한다.

[제품 계획의 이전 앱 기록](product-plan.md#개발-순서와-완료를-판단할-증거)은 특정 바이너리의 로컬 CEF, 네이티브 UI 성공이다. 이번 보완 전 소스의 [Rust 373개](../artifacts/keys-native-v1-rust-tests.json)와 [모의 DOM 128개](../artifacts/keys-native-v1-dom-summary.json)는 당시 소스 검증이다. 이번 후보에서는 전체 단위 회귀를 실행하지 않았고 해당 통과 수를 적용하지 않는다. [통합 빌드](../artifacts/ego-parity-v10-build.json)는 exit 0이며 [후속 확인](../artifacts/ego-parity-v10-postbuild.json)의 CLI help의 정상 응답을 확인했다. 이는 앱의 실제 입력 동작 확인이 아니다. [독립 Chromium 관찰](../artifacts/keys-native-v1-browser-summary.json)은 실제 제품 bridge를 사용했지만 Naru CEF와 AppKit을 실행한 결과가 아니다. [최종 정적 확인](../artifacts/keys-native-v1-final-static.json)도 같은 구분을 명시한다. e2e-v14 기준 단위 테스트는 `cargo test --locked --lib` 390개 통과다. 모의 DOM은 `node --test tests/dom_bridge.test.mjs`에서 101개 통과, 수정 전부터 있던 27개 실패가 남았다. 두 결과는 실제 앱 입력 확인이 아니다.

독립 Chromium의 지연 focus 경합 실패를 별도 조건에서 성공한 준비 거절 검사로 덮지 않는다. 07번 여정에서 실제 영향을 확인하고 지원 범위를 결정하기 전에는 배경 키 입력의 신뢰성을 완료로 표시하지 않는다. 메모리 수치도 RSS 합계를 고유 RAM으로 표시하지 않는다. 같은 조건으로 비교하지 않은 ego lite보다 가볍다는 결론은 내리지 않는다. 지속 증가나 회수 실패가 남으면 14번은 `fail` 또는 원인 미확인의 `blocked`다.

## 완료 판단과 제외 범위

아래 14개 여정은 첫 통합 검증의 최소 관문이다. 이를 통과한 사실만으로 ego lite 수준 전체 완료를 선언하지 않는다. 교차 출처 iframe 제어, 복잡한 편집기와 추가 키 조합 등 현재 미지원으로 적은 기능은 잔여 구현 목록이며 자동으로 목표에서 제외하지 않는다. 실제 ego lite 비교와 대표 웹 작업에서 필요한 범위를 확인하고, 구현하거나 사용자가 범위 변경을 선택해야 한다. 사용자가 명시적으로 보류한 탭 복원과 확대는 별도로 유지한다.

같은 최종 앱에서 지원 범위에 해당하는 행을 통과하고 증거와 정리를 남겨야 독립 사용 준비를 판단한다. P0에 `pending`, `fail`, `blocked`가 남으면 완료가 아니다. 사용자 선택 변경, 잘못된 입력 대상, 중지 뒤 늦은 조작, 데이터 손실, 미확정 파일 저장과 지속 자원 누적은 핵심 실패로 기록한다. P1 사용성 확인이 남으면 그 범위를 명시한 개발판으로 보고한다. 중지와 화면 보존 실패를 테스트 개수나 다른 행의 성공으로 상쇄하지 않는다.

재시작 탭 복원과 페이지 확대는 사용자 보류를 유지한다. 지원 밖 프레임 좌표 변환, 닫힌 Shadow DOM 내부 관찰, 지원 목록 밖 키와 조합, 범용 편집기의 서식과 undo 보존, 계정별 프로필 격리는 현재 미지원이다. AI 모델 연결, 내장 대화, 작업 메모리와 반복 작업의 전체 기능, 확장 기능 관리까지 최신 ego lite와 같다고 설명하지 않는다. 배포, 서명과 공증의 실제 발행, 업데이트 배포는 이 실행 범위에 포함하지 않는다. 기존 서명 경로로 통합 앱을 실행할 수 없는 상태는 실행 차단 사유로 기록한다.

[Preseller 내장](preseller-integration.md)은 독립 브라우저의 이 기준을 충족한 다음 같은 화면과 브라우저 구현을 분리해 진행한다. 별도 창을 CLI로 제어하는 것만으로 Preseller 내장 완료를 대신하지 않는다. 실행을 마칠 때 [작업 기록](work-log.md)에 요청 범위, 실제 변경, 통과와 실패, 미실행 이유, 남은 한계, 프로세스와 생성물 정리를 남긴다.
