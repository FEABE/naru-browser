# 다운로드 구현과 검증 계획

기준일: 2026-10-11. 현재 검증 대상은 `downloads-v4`이며 앱 SHA-256은 `e91508161347b45b6de4a32652915c828cf1aef949dffa8f14696bf97d42e471`다. Rust 검사 164개와 전체 타깃 검사, release 빌드를 통과했다. 사용자 키체인 승인 후 같은 ID의 실제 재시도, 실패 표시, 정상 저장과 진행 중 취소를 확인했다. 같은 최종 앱의 기존 CEF 회귀 32개와 재시작·정리도 통과했다. 모든 동시성·외부 서비스 검증이 끝났다는 뜻은 아니다. 이전 Rust 162개 통과는 두 FFI 수정 전인 v1 소스의 결과다.

작업 시작 시 `BrowserClient`에는 DownloadHandler가 없었으며 설치된 CEF 156의 공개 계약상 Alloy 브라우저는 이 경우 다운로드를 취소한다. 파일 업로드 선택창은 별도의 DialogHandler가 없어 CEF 기본 구현에 위임한다.

## 사용자 흐름

사용자 페이지와 AI 페이지에서 발생한 다운로드를 브라우저의 다운로드 목록에 접수한다. 배경 AI 작업이 저장창이나 다른 공간을 자동으로 열지 않는다. 사용자가 다운로드 목록에서 **저장 위치 선택**을 누르면 CEF 기본 네이티브 저장창을 열고, 선택한 경로로 다운로드를 진행한다. 다운로드 목록 열기와 저장 위치 선택은 브라우저 관리 동작이며 AI 작업을 자동으로 중지하지 않는다.

목록은 파일 이름, 출처 공간, 상태와 받은 크기를 표시한다. 전체 크기가 알려진 경우에만 진행률을 표시한다. 진행 중인 항목은 취소할 수 있고, 완료·취소·실패 기록은 목록에서 지울 수 있다. 기록 지우기는 저장된 파일을 삭제하지 않는다. 파일을 자동 실행하거나 외부 프로그램으로 열지 않는다.

## 수명과 자원

- 접수 대기와 진행 중인 항목은 합쳐 최대 4개, 완료 기록을 포함한 메타데이터는 최대 24개다. 상한에 도달하면 새 요청을 거절하며 진행 중인 항목을 조용히 제거하지 않는다.
- 이름은 최대 256자, 표시 경로는 최대 8,192바이트다. 원본 URL·파일 내용·`DownloadItem` 객체·각 행의 Browser 객체를 보관하지 않는다. 실제 저장은 CEF에 맡기며 표시용 경로로 파일을 쓰지 않는다.
- v4는 사용자가 저장창에서 승인한 경로를 `approved_path`로 별도 보관한다. 활성 콜백 최대 4개에 각각 8,192바이트 이하이며, 경로 내용의 상한 합계는 32KiB다. 메타데이터와 할당 오버헤드를 포함한 전체 메모리 측정값은 아니다. `DownloadItem::full_path`로 받은 진행 경로를 저장 승인으로 사용하지 않는다.
- 네이티브 저장창은 한 번에 하나다. `RunFileDialog(SAVE)` 완료 콜백에서 닫힘을 확인하고, 유효한 선택만 원래 `BeforeDownloadCallback`으로 전달한다. 저장창을 취소하거나 그 사이 작업/탭이 만료되면 선택한 최종 경로로 저장을 시작하지 않는다. 경로 선택 전 Chromium의 응답 수신과 임시 버퍼까지 중지한다는 뜻은 아니다.
- active AI 작업에서 시작된 요청은 작업 ID와 revision을 연결한다. 해당 작업의 인계·해제·완료 시 대기와 진행 중인 다운로드를 취소한다. 직접 사용 중인 paused 탭의 새 요청은 사용자 요청으로 다룬다.
- 탭 닫기를 요청한 순간에는 취소하지 않는다. beforeunload의 닫기 승인이 끝난 `do_close`에서 해당 탭의 다운로드를 취소하고 `on_before_close`에서 정리한다. 앱 종료 시 CEF 종료 전에 콜백 참조를 해제한다.
- 취소는 요청 상태와 CEF 확인 상태를 구분한다. 늦은 콜백은 종료되거나 제거된 항목을 다시 진행 중으로 만들지 않는다. 콜백 호출과 해제는 상태의 RefCell borrow 밖에서 수행한다.
- 별도 DB, 영속 다운로드 이력, worker, 타이머, UI renderer를 추가하지 않는다. 목록은 앱 재시작 시 초기화하며 저장한 파일은 그대로 둔다. Chromium의 다운로드 버퍼·파일 처리 전체 메모리가 이 메타데이터 상한으로 제한된다는 뜻은 아니다.

## v4 재시도 계약

CEF가 진행 중인 같은 다운로드 ID로 `OnBeforeDownload`를 다시 호출하면 기존 항목의 탭, `Downloading` 상태, 취소 여부와 승인 경로를 확인한다. 작업 ID와 revision도 다시 검증한 뒤 같은 승인 경로로 콜백을 계속한다. 목록 항목과 활성 슬롯을 추가하거나 새 저장창을 자동으로 열지 않는다.

취소 요청 중인 항목, 끝난 항목, 다른 탭, 저장 승인이 없는 항목, 앱 종료 중에는 재개하지 않는다. 이 처리는 CEF가 전달한 반복 콜백에 대한 소스 계약이며 자체 재시도 타이머나 큐를 만들지 않는다. 순수 Rust 검사는 최대 4개 상태에서 같은 승인 경로를 재사용하는 경우와 취소, 종료, 미승인, 다른 탭 거절을 다룬다. v4의 실제 실패 응답에서는 다운로드 ID 16의 최초 콜백 1회와 `Some(Downloading)` 상태의 반복 콜백 5회를 확인했다. 횟수는 해당 fixture에서 관찰한 값이며 모든 다운로드의 고정 재시도 횟수라는 뜻은 아니다.

## 검증할 항목

순수 모델 검사는 상한, 끝난 항목부터 제거하는 순서, 잘못된 수치, terminal 이후 늦은 업데이트, 취소와 저장창의 경합, 작업/탭 수명을 다룬다. 앱 검사와 구분해 기록한다.

`tests/download_fixture.py`는 로컬 HTML과 고정 attachment만 제공한다. 작은 파일의 SHA-256, 느린 응답, 선언한 크기보다 일찍 끊기는 응답, 읽기 전용 서버 상태를 제공한다. 다운로드 취소·실패 검사는 서버 전송 상태와 실제 UI 상태를 함께 확인한다. 저장 대상은 해당 검증에서 만든 workspace 파일로 제한한다.

네이티브 검사는 저장창 취소, 파일 저장과 해시 일치, 진행 표시와 취소, 실패 표시, 완료 기록 지우기, 배경 AI 다운로드의 사용자 화면 보존, 작업 중지와 열린 저장창의 늦은 응답, 탭 닫기/닫기 취소를 포함한다. 기존 폼 선택·공간·작업·단일 창 검사를 같은 최종 바이너리에서 실행한다. 기본 파일 선택창도 별도 결과로 기록하며 AI의 파일 입력 지원으로 확대하지 않는다.

## v3에서 확인한 결과

v3 앱 SHA-256 `83522cdfce1f959f6b0ec3bf7baa276f08e193618b9e82c035fd61477a58ae89`에서 로컬 fixture와 실제 네이티브 UI로 다음 동작을 확인했다. 외부 사이트나 장시간 전송의 검증은 아니다.

- 작은 파일을 저장해 131,072바이트와 SHA-256 `59f410ae5e17962412e2aed4f815918f634932f2abf084f00bb638c4db017850` 일치를 확인했다.
- 저장창을 취소한 뒤 진행 항목이 0개가 됐다.
- 느린 8,388,608바이트 응답에서 2,424,832바이트, 28% 진행 표시를 확인하고 취소했다. 이후 진행 항목과 서버의 활성 전송이 0개가 됐으며 서버 연결 종료를 확인했다. 검증 저장 위치에 해당 부분 파일은 남지 않았다.
- 완료 기록을 지운 뒤에도 앞서 저장한 작은 파일은 유지됐다.
- 페이지의 네이티브 파일 선택창으로 같은 131,072바이트 파일을 선택했고 `isTrusted: true` 입력 이벤트를 확인했다. AI 명령으로 파일을 올리는 기능을 검증한 것은 아니다.
- 배경 AI 작업에서 다운로드가 대기 상태가 됐을 때 사용자 공간과 선택된 사용자 탭 2가 유지됐다.
- AI 요청의 저장창을 연 뒤 작업을 사용자에게 인계했다. 이후 저장창에서 늦게 Save를 눌러도 다운로드는 취소됐고 해당 파일은 생기지 않았다.
- beforeunload 경고에서 닫기를 취소하면 탭과 대기 다운로드가 유지됐다. 이어 닫기를 승인하자 실제 탭 닫기와 함께 다운로드가 취소됐고 진행 항목은 0개가 됐다.
- v3 앱 종료 코드 0을 확인했다. 종료 시 활성 다운로드가 있는 모든 경합을 검증했다는 뜻은 아니다.

저장과 취소 결과, 바이너리 해시, fixture 상태는 `artifacts/downloads-v3-validation.json`에 기록했다. v3 release 빌드 근거는 `artifacts/downloads-v3-build.log`다. v3의 `nativeValidationComplete`는 `false`이며 실패 응답 결함을 다음 버전에서 검증했다.

## v4에서 확인한 결과

- 크기보다 일찍 끊기는 응답에서 같은 ID의 실제 재시도 후 `Interrupted`, 원인 코드 38이 표시됐다. 진행 항목은 0개였으며 잘못된 최대 4개 제한 문구와 부분 파일은 없었다.
- 정상 파일은 `Complete`와 진행 항목 0개를 확인했다. 저장된 131,072바이트 파일의 SHA-256이 위 작은 파일과 일치했다.
- 느린 응답에서 2,293,760바이트, 27% 진행을 확인한 뒤 취소했다. 진행 항목과 서버 활성 전송은 0개였고 해당 부분 파일은 남지 않았다. 서버 연결 종료 수 2는 v3부터 사용한 fixture의 누적값이다.
- 완료 기록을 지운 뒤에도 정상 저장한 파일은 유지됐다.

근거는 `artifacts/downloads-v4-validation.json`과 `artifacts/downloads-v4-app.log`다. Rust 164개 통과는 `artifacts/downloads-v4-rust-tests.log`에 기록했다. 기존 CEF 회귀 select 10개·tasks 6개·spaces 10개·single_window 6개도 같은 바이너리에서 통과했다. 자체 작업 9개와 탭을 정리했다. 동일 바이너리 재시작에서 HTTP 완료와 빈 다운로드 목록·최근 닫은 탭 기록을 확인했다. 근거는 `artifacts/downloads-v4-suite.json`, `-suite-state.json`, `-restart.json`이다.

테스트 fixture는 요청줄과 헤더를 읽기 전부터 3초 timeout을 적용한다. 빈 연결 두 개를 유지한 독립 HTTP 종료 검사에서 SIGTERM 뒤 3.012초·exit 0을 확인했다(`artifacts/downloads-v4-fixture-shutdown.json`). 실제 CEF 다운로드 검사와 별도 결과다.

## 확인된 결함과 남은 검증

- v3의 실패 응답 오표시는 v4의 같은 ID 재시도와 `Interrupted` 표시로 수정 결과를 확인했다. 검증 범위는 해당 로컬 fixture다.
- 이전 v2에서 합성 클릭의 연속 다운로드가 접수되지 않았다. MULTIPLE_DOWNLOADS 권한 콜백 진입을 아직 관찰하지 않아 원인은 확정하지 않았다. 전역 자동 허용을 적용하지 않았으며 명시적 권한 UI가 후속 과제다.
- 다운로드 패널을 열 때 AppKit의 음수 width와 height 경고가 관찰됐다. 초기 빈 라벨 생성 경로를 후보로 검토했으나 경고의 호출 스택을 확인하지 못했다. 라벨 생성 변경은 보류했으며 원인이나 표시 영향이 해결됐다고 판단하지 않는다.
- v3에서 확인한 배경 화면 보존, 저장창을 연 상태의 인계, beforeunload 흐름을 v4에서 다시 확인해야 한다. 별도 작업 중지, 해제, 완료와 앱 종료 중인 전송의 콜백 경합도 남아 있다.
- v4의 Rust 164개와 전체 타깃 검사, release 빌드, 위 네이티브 흐름은 통과했다. 기존 CEF 회귀 32개와 v4 재시작 검증도 통과했다.
- 외부 서비스, 좁은 창의 다운로드 패널, 장시간 전송과 전후 메모리 변화는 검증하지 않았다. 빈 탭 RSS 표본은 별도 [메모리 문서](memory.md)에 기록했다. 현재 설계의 최소 창 크기와 메타데이터 상한은 실제 네이티브 검증 결과와 구분한다.

## 근거

설치 버전의 `.cache/cef/156.0.1/cef_macos_aarch64/include/cef_client.h`, `cef_download_handler.h`, `cef_download_item.h`, `cef_browser.h`, `cef_dialog_handler.h`와 현재 Rust 바인딩을 기준으로 한다. 공개 헤더의 콜백 계약, 순수 모델 검사, 로컬 CEF 실행, 네이티브 UI 확인을 구분한다. 수정과 후속 실행 결과가 나오면 해당 버전의 증거로 갱신한다.

## v4 빌드와 승인 상태

v4 빌드에서 4,332개, 2.5GiB를 정리했다. 첫 HTTP는 commit 전 5초 `WAIT_TIMEOUT`이었고 새 SecurityAgent가 떠 키체인 승인을 기다렸다. 사용자가 승인한 뒤 같은 바이너리로 위 네이티브 검증을 진행했다. 이번 승인 대기는 해소됐지만 재서명 후 승인 요청 자체를 없앴다는 뜻은 아니다. 상태와 실행 핸들은 `artifacts/downloads-v4-validation.json`에 남겼다.
