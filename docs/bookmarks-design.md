# 북마크 저장 설계

기준일: 2026-10-11. **사용자가 기존 데이터 폴더의 JSON 파일 방식, 정상 백업 한 개, 모든 공간 공유, 최대 1,000개와 2MiB를 승인했다.** 저장 모듈과 AppKit UI·비동기 런타임을 연결한 북마크 v1은 Rust 검사 124개와 release 빌드를 통과했다. 사용자 승인 후 같은 앱에서 실제 추가·편집·검색·열기·삭제, 정상 종료 뒤 두 항목 보존과 마지막 항목 삭제 뒤 빈 목록 유지를 확인했다. 검증용 손상 프로필에서는 읽기 전용 UI와 원본 파일 보존을 확인했다. v2의 통합 검색 실행 결과와 v3 포커스 수정의 검증 범위는 아래에서 구분한다.

## 현재 구조에서 확인한 점

- `src/config.rs`의 `data_dir()`는 `LIGHT_BROWSER_DATA_DIR`가 있으면 그 값을 사용한다. 없으면 `$HOME/Library/Application Support/Light Browser`를 사용한다. 상대 경로 환경값은 현재 실행 디렉터리를 기준으로 절대 경로로 바꾼다.
- `src/main.rs`는 이 폴더의 `control.sock`을 바인딩한 뒤 `profile-v1`을 만든다. CEF에는 `profile-v1/default`를 cache path로 전달하고 세션 쿠키 보존을 켠다. 기존 Chromium 프로필 파일을 북마크 저장 파일로 사용할 근거는 없다.
- `src/browser.rs`의 `State`는 탭, 작업, 공간을 메모리에 보관한다. 이번 `src/bookmarks.rs`는 그 상태와 별개인 owned `Store`를 추가한다. `src/capture.rs`는 새 PNG 파일을 만드는 경로이므로 북마크 교체 코드로 재사용하지 않았다.
- CLI는 `src/bin/cli.rs → config::socket_path → cli::run → protocol::call → browser::serve_connection → CommandTask::execute → handle`로 앱에 요청한다. 같은 데이터 폴더에 살아 있는 서비스가 있으면 `protocol::bind_listener`가 두 번째 실행을 거절한다.

## 승인된 저장 위치와 공유 범위

앱 데이터 폴더에 JSON 파일 하나와 직전 정상본 백업 하나를 둔다. 기존 `serde`, `serde_json`, Rust 표준 라이브러리를 사용하며 저장을 위한 새 DB나 별도 상주 프로세스는 추가하지 않는다.

| 용도 | 경로 |
| --- | --- |
| 기본 북마크 파일 | `$HOME/Library/Application Support/Light Browser/bookmarks-v1.json` |
| 기본 백업 파일 | `$HOME/Library/Application Support/Light Browser/bookmarks-v1.json.bak` |
| 경로 재정의 시 | `config::data_dir()`가 반환한 폴더 아래 같은 파일명 |
| 저장 중 임시 파일 | 같은 폴더의 `.bookmarks-v1.json.pending`, `.bookmarks-v1.json.bak.pending` |

현재 환경에서 기본 경로의 `$HOME`은 `/Users/sherpa`다. 구현에서는 이 값을 하드코딩하지 않는다. `profile-v1/default` 내부의 Chromium 파일과 쿠키, 로그인 데이터는 수정하지 않는다.

북마크는 같은 `data_dir`를 사용하는 내 공간과 모든 AI 작업 공간에서 공유한다. 공간 ID나 작업 ID에 묶어 복제하지 않으며, 작업 종료로 북마크가 삭제되지 않는다. 다른 `LIGHT_BROWSER_DATA_DIR`를 사용하는 실행과는 별도 목록이 된다. 이는 현재 데이터 폴더 단위의 공유 정책이며 계정별 보안 격리를 뜻하지 않는다.

첫 범위는 사용자 UI의 추가, 저장 이름 수정, 열기, 삭제, 검색과 재실행 보존이다. 폴더, 가져오기, 내보내기, 동기화, favicon, 썸네일, AI 작업의 자동 북마크 변경은 후속 범위로 둔다. CLI 관리 명령을 추가한다면 앱의 기존 요청 경로를 사용한다. CLI가 JSON 파일을 직접 수정하지 않는다.

## 데이터 형식과 상한

```json
{
  "version": 1,
  "nextId": 2,
  "items": [
    {
      "id": 1,
      "title": "예시 북마크",
      "url": "https://example.com/"
    }
  ]
}
```

| 항목 | 승인·구현 정책 |
| --- | --- |
| 목록 수 | 최대 1,000개 |
| 파일 크기 | 직렬화된 JSON 전체 최대 2MiB, 읽기에도 같은 상한 적용 |
| URL | 정규화 결과 UTF-8 최대 8,192바이트 |
| 제목 | 앞뒤 공백을 제거한 뒤 1~256 Unicode 문자, 제어 문자 금지 |
| ID | 양수 `u64`, 파일 안에서 중복 금지, 삭제한 ID 재사용 금지 |
| nextId | 기존 모든 ID보다 커야 함, 증가할 수 없으면 추가 거절 |
| 정렬 | 저장된 배열 순서 유지, 첫 범위는 추가 순서 사용 |
| 검색 | 메모리 목록에서 제목과 URL 검색, UI에는 최대 30개 결과만 전달 |

개별 항목 상한을 만족해도 전체 파일이 2MiB를 넘으면 저장을 거절한다. 이를 자동 잘라내기나 오래된 항목 삭제로 해결하지 않는다. 입력 제목과 현재 페이지 제목은 별개이며 페이지 제목이 바뀌어도 저장 이름을 덮어쓰지 않는다. 추가 UI의 기본 이름은 페이지 제목에서 가져오고, 없으면 URL 앞부분을 제목 상한에 맞게 제안한다.

읽기는 파일 전체를 제한 없이 가져오지 않는다. 최대 크기를 확인하고 읽기 자체도 상한보다 한 바이트까지만 허용해 초과를 판별한다. 항목 수와 필드 검증을 거친 목록만 메모리에 반영한다. 별도 검색 DB, 전체 소문자 복제 목록, 이미지 캐시는 만들지 않는다. 저장 중 생기는 이전 목록과 새 후보의 일시적인 복사까지 제한해야 하며 앱 전체 메모리 감소를 보장하는 수치로 설명하지 않는다.

## URL 정규화 정책

이번 변경에서 `address::normalize_url`을 추가했다. 명시적 HTTP(S) 주소를 입력하면 `control_panel::ShellTarget::navigate → address::resolve → address::normalize_url → address::web_url`을 거친다. scheme 없는 주소 보완은 기존 `resolve → web_url` 경로를 유지한다. `browser::valid_url`과 `cli::parse_url`의 허용 정책은 바꾸지 않았다.

북마크의 `Store::add`, `find_by_url`, 파일 검증은 검색을 수행하지 않는 `address::normalize_url`을 사용한다. 기존 `web_url`의 검증과 인코딩 로직을 재사용하며 명시적인 HTTP(S) URL만 받는다. **북마크 저장에는 `address::resolve`를 호출하지 않는다.** 이 함수는 일반 문자열과 검색 연산자를 Google 검색 URL로 바꾸기 때문이다. 검색 문자열 안의 모든 URL을 검사하는 기존 credentials 방어도 유지했다.

- scheme은 대소문자를 구분하지 않고 받은 뒤 `http` 또는 `https` 소문자로 저장한다.
- 사용자 이름이나 비밀번호가 있는 authority, 잘못된 host와 port, 제어 문자, 역슬래시는 거절한다. 빈 URL과 `about:blank`, `javascript:`, `data:`, `file:` 및 custom scheme도 저장하지 않는다.
- 경로와 query의 공백 및 비ASCII UTF-8 바이트를 percent encoding한다. 기존 `%HH`와 URL 구분자는 보존하고 잘못된 `%`는 `%25`로 처리한다. 인코딩 뒤 URL 상한을 다시 확인한다.
- 첫 버전에서는 host 소문자화, 기본 port 제거, 끝 슬래시 추가, query 정렬, fragment 삭제, 리다이렉트 목적지 추측을 하지 않는다. 이는 전체 URL 표준화 기능을 새로 만드는 범위가 아니다.
- 중복 판단은 위 처리 후의 URL 문자열이 완전히 같은 경우로 제한한다. 같은 URL을 다시 추가하면 기존 ID의 이름 편집 화면을 연다. URL 표기가 다르지만 실제로 같은 페이지인 경우를 자동 합치지 않는다.
- 새 탭 입력의 도메인 보완과 웹 검색 동작, CLI의 기존 URL 허용 정책은 이 북마크 설계로 변경하지 않는다.

예를 들어 `HTTPS://Example.com/a b?q=한글`은 scheme 소문자화와 경로, query 인코딩만 적용한다. `example.com`은 북마크 저장 API에서 거절하고, 주소창에서 먼저 실제 HTTP(S) 주소로 탐색한 뒤 저장하도록 한다. 정규화 helper를 추출할 때 기존 주소창 단위 검사를 함께 유지해야 한다.

## 저장과 실패 처리

앱이 유일한 쓰기 주체가 된다. `Store`는 owned 값이고 자체 스레드, UI, 타이머를 만들지 않는다. `bookmark_runtime`이 준비된 비공개 데이터 폴더를 받아 UI 스레드 밖에서 `load`와 변경을 실행한다. 변경은 한 건씩 처리하며 디스크 교체 전에는 기존 목록을 유지한다. 추가 요청을 대기열에 쌓지 않고 저장 중임을 알린다.

공개 API는 `Store::load(&Path)`, `items()`, `writable()`, `notice()`, `path()`, `find_by_url(&str)`, `add(url, title)`, `rename(id, title)`, `remove(id)`다. 변경 결과 `Mutation`은 `id`, `changed`, `durability_warning`을 돌려준다. 중복 추가는 기존 ID와 `changed=false`를 반환하고 저장 이름을 덮어쓰지 않는다. 새 목록은 완료된 `Store`에서 읽는다.

1. 변경 후보의 필드와 직렬화 크기를 검증한다. 데이터 폴더는 현재 사용자 소유의 비공개 디렉터리여야 한다. 기존 대상이 symlink, 디렉터리, 다른 사용자의 파일이면 쓰지 않는다.
2. `.bookmarks-v1.json.pending`을 `create_new`와 권한 `0600`으로 만든다. 후보를 기록하고 flush와 `sync_all`을 수행한다. 기존 pending 파일이 있으면 덮어쓰지 않는다.
3. 기존 정상 본문이 있으면 그 내용을 별도 backup pending 파일에 기록하고 동기화한 뒤 `.bak`으로 rename한다. 백업 파일 교체 전에도 기존 파일의 종류와 유효성을 확인한다. 첫 저장처럼 본문과 백업이 모두 없는 경우에는 백업 단계를 생략한다.
4. 백업 갱신이 성공한 뒤 새 본문 pending 파일을 `bookmarks-v1.json`으로 rename한다. 기존 본문을 먼저 `.bak`으로 옮겨 본문 경로가 비는 방식을 사용하지 않는다.
5. 본문 rename을 반영 시점으로 삼는다. 이어 부모 디렉터리 동기화를 수행한다. rename의 원자성과 전원 차단 뒤 영속성은 별도로 검증한다.

| 실패 시점 | 구현 동작 |
| --- | --- |
| 검증, 임시 파일 생성, 기록, 동기화 실패 | 기존 본문과 메모리 목록 유지. 저장 오류를 표시하고 이번 작업이 만든 임시 파일만 정리 |
| 백업 생성 또는 교체 실패 | 본문을 교체하지 않음. 메모리 목록도 유지. 이미 교체된 백업은 유효한 이전 본문일 수 있으므로 삭제하지 않음 |
| 본문 rename 실패 | 기존 본문과 메모리 목록 유지. 백업은 이전 본문 상태로 남을 수 있음. 이번 후보 임시 파일만 정리 |
| 본문 rename 성공 뒤 디렉터리 동기화 실패 | 새 본문과 메모리 상태를 일치시킴. “현재 파일에 반영됐으나 영속 동기화 확인에 실패함”을 구분해서 알림. 변경이 없었다고 보고하거나 무조건 재시도하지 않음 |
| 저장 도중 정상 앱 종료 | `main`에서 CEF 종료 전에 진행 중인 worker를 join하고 저장 결과를 회수. UI 완료 callback 실행에 의존하지 않음 |
| 강제 종료 등으로 저장 중단 | 다음 시작에서 본문과 백업을 다시 검증. pending 파일은 자동 채택하거나 덮어쓰지 않음 |

파일 정리는 현재 작업이 생성한 경로와 파일 종류, inode를 확인한 뒤 수행한다. 고정된 pending 이름을 사용하므로 실패 때마다 새 파일이 끝없이 누적되지는 않는다. 이전 실행의 pending 파일이 남으면 기존 본문은 읽을 수 있지만 추가 저장은 막고 복구 또는 정리가 필요함을 표시한다. 알 수 없는 기존 파일을 임의로 삭제하지 않는다.

외부 프로그램의 동시 편집과 여러 쓰기 프로세스는 첫 버전의 지원 범위가 아니다. 저장 전 외부 교체를 발견하면 중단하고 다시 읽도록 안내한다. 이것을 모든 외부 파일 수정과 경쟁 상태를 해결하는 잠금 규약으로 설명하지 않는다.

## 손상과 복구

| 시작 상태 | 구현 동작 |
| --- | --- |
| 본문과 백업이 모두 없음 | 처음 사용하는 빈 목록으로 시작 |
| 본문 정상 | 본문을 사용. 정상적인 빈 목록도 그대로 사용 |
| 본문이 없거나 손상됐고 정상 백업이 있음 | 백업 내용을 읽기 전용으로 표시하고 복구가 필요함을 알림. 원본 경로와 백업을 자동 교체하지 않음 |
| 본문과 백업 모두 손상 | 브라우저 탐색은 유지하되 북마크 저장을 차단하고 원인을 표시. 빈 정상 파일을 새로 쓰지 않음 |
| 미지원 version 또는 상한 초과 | 손상과 마찬가지로 원본을 보존하고 자동 이전이나 덮어쓰기 금지 |
| 본문 정상, 기존 백업 손상 | 본문은 읽을 수 있음. 손상 백업도 보존하고 백업 복구 또는 재생성을 결정하기 전까지 저장 차단 |

복구와 pending 파일 정리는 원본 보존 방법을 보여주는 별도 명시 동작으로 둔다. 손상 파일을 자동 이동하거나 번호를 붙여 계속 쌓지 않는다. 첫 버전에서 복구 UI를 구현하지 못하면 읽기 전용 상태와 파일 경로, 문제 원인까지 표시하고 복구를 완료했다고 보고하지 않는다.

삭제는 정상 목록에서 항목을 제거한 새 문서를 저장하는 변경이다. 마지막 항목을 삭제해도 본문 파일을 없애지 않고 `items: []`를 저장한다. 재실행 때 정상 빈 본문보다 이전 백업을 우선하면 삭제 항목이 되살아나므로 금지한다. 직전 상태 백업에는 방금 삭제한 항목이 남을 수 있으며 삭제를 복구 불가능한 영구 제거라고 설명하지 않는다.

## 네이티브 화면과 런타임 연결

사이드바의 북마크 버튼과 북마크 메뉴는 같은 창 안의 AppKit 화면을 연다. `⌘D` 또는 “현재 페이지 추가”는 `control_panel::open_bookmarks → bookmark_runtime::prepare → browser::bookmark_page`를 호출한다. 현재 제목을 브라우저 상태에서 복사하고, 상태를 빌린 범위를 벗어난 뒤 CEF main frame의 URL을 읽어 초안을 고정한다. 주소창에서 편집 중인 문자열이나 검색어를 저장하지 않는다. 현재 페이지가 `about:blank`이거나 허용하지 않는 주소이면 오류를 표시한다.

이미 저장한 URL은 기존 ID와 사용자가 정한 이름을 편집한다. 저장은 `control_panel::save_bookmark → bookmark_runtime::add/rename`, 목록 삭제는 `bookmark_runtime::remove`로 이어진다. 이후 페이지가 이동해도 열린 초안의 URL은 바뀌지 않는다. 저장 실패 시 초안을 유지하고 이름을 다시 고칠 수 있게 한다. 편집 취소와 목록 닫기는 UI의 요청 번호를 무효화하므로 이전 완료 응답이 새 편집 화면을 닫지 않는다. 이미 시작한 파일 저장은 UI를 닫아도 계속된다.

`main → bookmark_runtime::initialize(data_dir)`가 읽기 작업을 시작한다. 런타임은 `Store` 하나를 짧은 worker 하나에 이동시켜 `Store::load/add/rename/remove`를 실행한다. 작업 결과는 한 칸짜리 채널로 반환하고 CEF UI task를 게시한다. `Runtime::complete → control_panel::bookmark_completed`는 현재 작업 번호를 확인한 뒤 메모리 목록과 화면을 갱신한다. 생성 실패 때는 Store를 되찾으며, worker 실패로 결과가 불명확하면 저장을 차단하고 재실행 확인을 안내한다. 반영 후 동기화 경고는 성공한 변경과 함께 전달하며 재시도할 실패로 바꾸지 않는다.

메모리 목록은 작업 완료 때만 갱신하는 `Arc<[Bookmark]>` 캐시다. 화면 조회는 준비·저장 중·읽기 전용 여부, 전체 개수, 안내와 경로를 제공한다. 제목과 URL을 대소문자 구분 없이 검색하며 공백으로 나눈 모든 검색어가 일치해야 한다. 입력은 최대 200자, 별도 북마크 화면의 결과는 추가 순서대로 최대 30개만 복제한다. UI 행은 북마크 화면이 열렸을 때 유지하며 닫을 때 해제한다. 북마크 v1에서 한국어·URL 검색과 방향키·Enter·Esc 경로를 확인했다. IME 조합 중 제출 방어 코드는 있으나 실제 조합 입력은 아직 검증하지 않았다.

열기는 `bookmark_runtime::open(id) → browser::open_bookmark_url`로 이어진다. 내 공간에서 같은 URL을 가진 소유권 없는 정상 탭을 찾고 현재 선택과 일치하는 탭, 그다음 낮은 탭 ID 순으로 재사용한다. 중지됐거나 미완료 종료·탐색 오류·renderer 실패가 남은 탭은 재사용하지 않는다. 없으면 내 공간에 새 탭을 만든 뒤 명시적으로 내 공간과 해당 탭을 보여준다. AI 소유 탭이나 다른 공간의 탭은 재사용하지 않으며 AI 작업의 상태·revision과 각 작업 공간의 저장된 선택은 유지한다.

`main`은 CEF 메시지 루프가 끝나면 `bookmark_runtime::shutdown`에서 worker 종료를 기다린 뒤 CEF를 종료한다. worker의 파일 작업과 결과 전송에는 UI callback이 필요하지 않다. 별도 상주 worker·프로세스·반복 타이머·UI renderer는 추가하지 않았다. 다만 CEF의 완료 task 게시 자체가 실패하면 파일 작업은 끝나도 화면에 저장 중 상태가 남을 수 있으며, 정상 종료 시 join으로 회수한다. 이 실패 경계의 네이티브 재현은 아직 없다.

`⌘⇧A`는 열린 탭과 북마크 통합 검색이며 북마크 편집은 별도 화면이다. 소스의 `Shell::rebuild_search_results → tab_search::combined_results`는 기존 런타임의 북마크 결과와 열린 탭을 합쳐 탭 우선, 전체 최대 40개로 표시한다. 북마크 선택은 기존 `bookmark_runtime::open`을 사용한다. 사용자 승인 후 같은 v2 앱에서 숫자 ID가 같은 탭과 북마크의 독립 선택, 방향키·Enter·마우스, 사용자 탭 재사용과 새 사용자 탭 열기를 확인했다. 검색 중 현재 탭을 닫으면 입력 포커스를 잃는 결함은 v3에서 수정했다. 빈 탭과 HTTP 문서의 검색 입력, 북마크 이름 편집 중 원래 탭을 닫는 네이티브 회귀를 통과했다. 방문 기록 검색, 손상 파일을 다시 쓰는 복구 UI, CLI 북마크 명령은 구현하지 않았다.

## 검증 상태와 후속 계획

`artifacts/daily-browser-v6-rust-tests.log`에서 전체 117개 검사가 통과했다. 여기에 북마크 저장 모듈 9개 검사가 포함된다. 임시 디렉터리의 저장 후 새 Store 재로드, 마지막 항목 삭제, 손상 파일 보존, 단계별 실패 주입과 반영 후 경고를 실행했다. 실제 앱 재시작이나 전원 차단 검증을 대신하는 결과는 아니다. 초기 macOS `openat` variadic 권한 인자 타입 오류는 `libc::c_uint`로 수정했다.

위 117개 결과는 저장 모듈까지 포함하는 v6 기준이며 새 북마크 UI·런타임 연결은 포함하지 않는다. 새 소스에는 한 건 처리와 중복 요청 거절, 오래된 완료 번호 무시, 오류 후 Store 회수, 저장 직후 종료 대기, AI 제어권 보존, 중단된 탭 재사용 제외와 닫았다 다시 연 편집 화면 보호 회귀 검사를 추가했다. `artifacts/bookmarks-v1-rust-tests.log`에서 이 7개 회귀를 포함한 전체 124개 검사가 통과했다. release 빌드도 성공했다.

아래 실행 결과는 이전 북마크 v1 SHA-256 `bd7baf100fd434e0898fa98c9453988fb5b531ed205d5eea86f4e27f6c828dbd`다. `artifacts/bookmarks-v1-suite.json`에서 로컬 CEF 작업·공간·단일 창 22개 항목이 통과했다. 북마크 자체의 사용자 동작은 `artifacts/bookmarks-v1-native.json`에서 별도로 확인했다.

- `⌘D`로 실제 페이지 제목과 URL을 제안하고 빈 이름 저장을 거절했다. 오류 후 같은 URL의 초안을 유지해 수정·저장할 수 있었다. 같은 URL을 다시 열면 ID 1을 유지하며 이름만 수정했고 중복 항목을 만들지 않았다.
- 한국어 제목과 URL을 함께 검색하고 방향키·Enter로 선택했다. 일치 결과가 없을 때 Enter로 탐색하지 않았다. 같은 URL의 사용자 탭 2를 재사용했고, 그 탭을 닫은 뒤에는 새 unowned 사용자 탭 4를 만들었다. 두 경우 AI 작업은 active·revision 1과 선택 탭 3을 유지했다.
- URL A의 편집 화면을 연 상태에서 원래 탭을 B로 탐색한 뒤 저장해도 A의 이름만 바뀌었다. 이는 편집 초안 고정 검증이며 디스크 쓰기 도중 탐색이나 강제 종료를 재현한 결과는 아니다.
- 정상 `⌘Q` 종료는 exit 0이었고 같은 바이너리의 재실행에서 두 항목의 이름·ID·순서를 보존했다. 두 항목을 삭제한 뒤 다시 정상 종료·재실행했을 때 `items: []`, `nextId: 3`을 사용했고 백업에 남은 항목을 되살리지 않았다.

`artifacts/bookmarks-v1-recovery.json`은 별도로 만든 손상 프로필에서 읽기 전용·손상 안내, 추가·이름 수정·삭제 비활성화와 `⌘D` 편집 차단, 정상 백업 항목의 Enter 열기를 확인했다. 본문과 백업 두 파일의 해시는 검사 전·후 및 정상 종료 후 동일했다. exit 0을 확인한 뒤 검증용 프로필만 삭제했다. 원본을 복구해서 다시 쓰는 기능을 실행한 것은 아니다.

통합 검색과 미리보기 v2는 Rust 128개, `cargo check --all-targets`, release 빌드를 통과했다. 해당 바이너리의 SHA-256은 `f9168ced388db274d3d18538a792081c7b5302bffc6b7817b4a59616c9227f74`다. 첫 탐색은 승인 전 `WAIT_TIMEOUT`이었지만 사용자 승인 후 같은 바이너리에서 검증을 이어갔다. `artifacts/search-preview-v2-native.json`에서 탭 3과 북마크 3을 독립적으로 선택하고 기존 사용자 탭 재사용·새 탭 생성 시 AI 작업의 active·revision 1·선택 탭 3을 유지했다. 일치 결과 없는 Enter와 Tab·ShiftTab 이동도 확인했다. 검증용 북마크 3은 삭제해 본문이 `items: []`, `nextId: 4`로 남았고 자체 작업을 종료했다. v2 앱은 exit 0으로 종료했다.

`artifacts/search-preview-v2-suite.json`의 로컬 CEF 작업·공간·단일 창 22개가 통과했고, `artifacts/search-preview-v2-suite-state.json`에서 기존 사용자 탭과 정리 후 캡처·생성 예약 0을 확인했다. `artifacts/search-preview-v2-delays.json`에서는 응답 헤더나 이미지 로딩을 기다리는 카드가 안내 화면을 유지하다가 각각의 POST 해제 후 실제 문서 미리보기로 바뀌었다. 공간 목록은 다시 열지 않았다. 이 결과는 과거 승인 대기나 캡처 정체의 원인을 확정하거나 메모리 절감을 측정한 것이 아니다.

v2에서 검색어를 입력한 채 기억된 현재 탭 2를 닫으면 결과와 검색어는 유지됐지만 포커스가 창으로 바뀌어 추가 입력을 받지 못했다. v3는 닫는 CEF 뷰 안에 실제 first responder가 있을 때만 포커스를 해제하도록 수정했다. 현재 `dist`와 실행 앱의 SHA-256은 `93bbf74352f3565713a24b4c9b20729e2b7bb627f8b771c7f91f35ebb9b9a9bd`다. Rust 128개, 전체 타깃 검사와 release 빌드가 통과했고 빌드 중간 파일 4,332개·2.4GiB를 정리했다. 최초 샌드박스 검사의 소켓 bind 권한 오류 3건과 재실행 성공을 각각 `artifacts/search-preview-v3-rust-tests-sandbox.log`, `artifacts/search-preview-v3-rust-tests.log`에 보존했다. 전체 타깃과 빌드 기록은 `artifacts/search-preview-v3-check.log`, `artifacts/search-preview-v3-build.log`다.

`artifacts/search-preview-v3-native.json`에서 빈 사용자 탭의 통합 검색과 빈 북마크 목록을 연 뒤 CLI로 탭을 닫아도 필드 포커스와 추가 붙여넣기를 유지했다. 첫 HTTP 탐색은 5초 `WAIT_TIMEOUT`이었지만 사용자가 키체인을 항상 허용한 뒤 같은 바이너리에서 탭 3의 로딩 완료를 확인했다. 이번 승인 대기는 해소됐다. 재서명 후 승인 요청을 없앤 결과는 아니다.

같은 v3의 통합 검색에서 사용자 탭 3·AI 탭 5·북마크 4를 확인했다. 탭 3을 닫아도 검색어와 입력 포커스를 유지했고 추가 붙여넣기가 반영됐다. “저장” 검색의 북마크 하나를 Enter로 열어 사용자 탭 6을 만들었으며 AI 작업의 active·revision 1·선택 탭 5를 보존했다. `⌘D`로 편집 중 탭 6을 닫아도 이름 필드의 포커스·선택과 고정 URL을 유지했다. “초안 유지”로 저장한 파일에서 ID 4와 원래 URL A를 확인했다. 검증 북마크는 UI로 삭제해 `items: []`, `nextId: 5`로 남겼고, AI 작업은 `finished`, `tabs: []`로 정리했다. 한글은 붙여넣기로 입력했으며 IME 조합 검증은 아니다.

`artifacts/search-preview-v3-suite.json`에서 같은 v3의 로컬 CEF 작업 6개·공간 10개·단일 창 6개, 총 22개가 통과했다. 세 묶음은 모두 exit 0이고 stderr는 비어 있다. `artifacts/search-preview-v3-suite-state.json`의 최종 상태는 기존 사용자 빈 탭 1 하나, `overview:false`, 대기 요청·캡처·탭 생성 예약 0이다. 회귀 검사가 만든 작업 7개는 모두 `finished`이며 `tabs`와 `closingTabs`가 비어 있다. 이후 v3의 ⌘Q 정상 종료 exit 0과 같은 바이너리의 재실행을 별도로 확인했다. 네이티브 목록은 빈 상태였고 백업의 삭제 항목은 되살아나지 않았다. 재실행 후 HTTP 탐색은 검사하지 않았다.

| 네이티브 UI 확인 | v1의 ⌘D·고정 초안·편집·검색·삭제·읽기 전용·재실행 보존 확인. v2 통합 검색의 탭·북마크 독립 선택, 키보드·마우스, 탭 재사용·새 탭과 AI 상태 보존 확인. v3의 빈 탭·HTTP 탭 닫기 후 검색 입력, 원래 탭 닫기 후 북마크 이름 편집·URL 고정·저장 통과. IME, 쓰기 중 강제 종료, 지연 완료와 반복 닫기·재열기는 남음 |
| 모의 DOM 검사 | 북마크 저장 자체에는 DOM bridge 변경이 없음. bridge를 수정하지 않았다면 이 기능의 저장 검증으로 대신 사용하지 않음 |
| 외부 사이트 확인 | 별도 범위. 로그인 페이지와 외부 서비스의 북마크 열기를 로컬 CEF 검사 성공으로 간주하지 않음 |

검증이 만든 항목·작업·탭만 정리하며 기존 사용자 데이터와 프로필은 보존한다. 손상 검사는 전용 임시 데이터 폴더에서 진행했다. 실제 앱을 빌드하거나 실행하면 해당 검증 앱과 이전 프로젝트 프로세스, 불필요한 빌드 산출물의 정리 결과를 작업 기록에 남긴다.

북마크 v1의 저장·검색·재시작 보존·손상 시 읽기 전용 경로와 v2의 통합 검색·지연 페이지 미리보기를 로컬에서 확인했다. v3는 사용자 승인 후 HTTP 로딩, 검색·북마크 편집 포커스와 CEF 22개 회귀까지 통과했다. v3 정상 종료와 빈 북마크 목록 재실행도 확인했다. IME·외부 서비스·장시간 부하·실제 쓰기 진행 중 종료 검증은 남아 있다. 방문 기록과 복구 UI는 미구현 범위다. [개발 계획](product-plan.md)에서 소스 검사와 앱 실행 증거를 구분한다.
