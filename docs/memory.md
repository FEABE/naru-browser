# Naru 메모리 관리

Naru는 Rust로 앱과 CLI를 구현하지만 웹페이지의 DOM, JavaScript, 이미지, GPU 자원은 Chromium이 관리한다. Rust 사용만으로 브라우저 전체 메모리가 작아지는 것은 아니다. 현재 제한은 자동화가 늘리는 CEF 탭, 큰 응답 버퍼의 겹침, 페이지 관찰과 공간 미리보기의 추가 자원에 적용한다. 브라우저 창 하나 안에서도 각 페이지는 별도의 CEF browser ID를 유지한다. 표시 공간을 나누어도 프로필이나 Chromium 엔진을 추가로 실행하지 않는다.

## 체크박스와 라디오 제어

`check`는 기존 참조와 페이지 요청 수명을 재사용한다. read의 체크박스에 혼합 상태 boolean을 추가하고 각 ref에 읽기 세대를 보관한다. 한 동작에서 클릭은 최대 한 번이며 라디오 그룹 배열이나 별도 DOM 캐시를 만들지 않는다. 요청에 종류 boolean 하나, 오류에 최대 네 boolean을 전달한다. 새 worker, 타이머, renderer와 저장 파일은 없다. 실제 Naru RAM 비교는 미실행이며 독립 Chromium의 동작 검사를 메모리 절감 근거로 사용하지 않는다. [계약과 검증](check-control.md)을 따른다.

## 페이지 우클릭 메뉴

탭마다 메뉴 세대 u64와 선택 대상 Option 하나를 추가한다. 대상에는 탭, 공간, 두 탐색 세대, 소유 작업 메타데이터와 프레임 ID를 보관한다. 링크 열기 항목에는 최대 8,192바이트 URL 하나를 추가하며 본문, CEF Browser, Frame, params와 model 참조는 보관하지 않는다. 명령 소비, 메뉴 종료와 다음 열기, 탭 닫힘에서 해제한다. 네이티브 getter 결과는 검사 중에만 사용한다. 새 메뉴 renderer, worker, 반복 타이머와 파일 저장은 없으며 실제 RAM 비용은 측정하지 않았다. [메뉴 제어권 계약](context-menu-control.md)을 따른다.

링크 주소 열기를 수락하면 URL과 고정 공간, 소유권 메타데이터를 기존 UI 큐 작업으로 넘긴다. 추가 CEF 탭은 명시적인 사용자 요청 한 번에 하나이며 사용자 생성에는 기존 자동화 탭 예산을 적용하지 않는다. 링크 메타데이터의 크기 제한이 탭 전체 메모리나 큐 개수 제한은 아니다. 실제 반복 생성과 닫힘 후 자원 회수는 최종 앱에서 확인해야 한다.

## 탭 표시 순서

공간마다 탭 ID Vec 하나, 메뉴 대상 최대 두 개를 추가한다. 소속 맵과 기존 UI 스냅샷은 유지하고 번호 선택·탭 순환용 목록을 따로 저장하지 않는다. 빈 배열은 해제하며 capacity가 32를 넘고 길이가 1/4 이하로 줄었을 때만 길이의 두 배를 기준으로 축소 요청한다. 새 worker, 타이머, 웹 renderer와 파일 저장은 없다. 순수 상태 검사의 배열 회수를 앱 전체 RAM 절감량으로 설명하지 않는다. [표시 순서 설계](tab-order.md)와 작업 기록에서 실제 앱 미검증 범위를 구분한다.

드래그 정렬은 기존 탭 행마다 네이티브 제스처 하나와 창당 삽입선 하나를 재사용한다. 동시에 한 세션만 표시 순서의 ID 배열을 보관하고 포인터 이동에서는 Rc를 공유하므로 배열을 다시 복제하지 않는다. 드롭은 기존 Vec 구간을 회전하며 선택이나 페이지 메모리를 바꾸지 않는다. 페이지 캡처와 드래그 이미지는 추가하지 않는다. 가장자리 자동 스크롤 중에만 네이티브 타이머 하나를 보관하고 중앙과 문서 끝, 드롭과 취소 때 invalidate한다. 같은 타이머를 두 run loop mode에 등록하며 타이머마다 탭 목록을 복제하지 않는다. 실제 AppKit 할당량과 브라우저 RAM 변화는 미측정이다.

## iframe 관찰의 자원

2026-10-15 소스는 한 read에서 최대 16개 iframe 문맥과 메타데이터, 깊이 8까지의 부모 연결을 보관한다. 기존 120개 refs는 요소와 원문서 문맥을 묶어 다음 read에서 교체한다. 기존 전체 노드, 본문, 옵션, Shadow DOM 예산을 모든 문서가 공유하며 문서마다 Range와 스타일의 임시 캐시를 사용한다. child WindowProxy 조회로 기존 renderer 안의 isolated context가 추가될 수 있다. 반복 read가 다른 프레임에 접근하면 context가 더 생길 수 있으므로 전체 context 16개 상한이 아니다. 전체 페이지 메모리나 context 크기를 제한하는 기능은 아니며 실제 RAM 비교는 미실행이다. 별도 worker, 타이머, renderer나 저장 파일을 만들지 않는다. [iframe 설계](iframe-control.md)를 따른다.

## 탭 음소거

2026-10-15 소스는 탭마다 마지막 확인 설정 `Option<bool>` 하나를 추가한다. 메뉴를 열 때 대상과 예상값 하나를 보관하고 실행 시 꺼내며 다음 열기나 앱 UI 종료 때 해제한다. 대상에는 ID, 공간, 탐색 세대와 소유권만 있고 Browser나 Frame, 오디오 버퍼는 없다. 네이티브 메뉴 한 항목과 기존 행 아이콘을 사용한다. 소리 분석, PCM 캡처, 별도 renderer와 worker, 반복 타이머, 파일 저장을 추가하지 않았다. 실제 프로세스 RAM과 소리 출력 비용은 측정하지 않았다. [탭 음소거 계약](tab-audio.md)을 따른다.

## 다운로드 관련 탭 확인

2026-10-15 소스는 파일 기록 최대 24개에 접수 당시 대상 하나씩, 탭마다 출처 세대 u64 하나를 추가한다. 대상은 탭 ID, 두 세대와 제한된 작업 ID, revision, 상태이며 URL, 본문, Browser 객체는 없다. 권한의 최대 4개 기존 대상은 그대로 조회한다. 목록을 열어 갱신할 때 최대 24개 대상의 임시 복사로 유효성을 확인하고 해제하며, 닫힌 목록에서 새 조회나 반복 타이머를 실행하지 않는다.

파일과 권한 행에 각각 네이티브 버튼 하나를 추가해 최대 28개이며 ID별 재사용과 패널을 닫을 때 행 해제를 유지한다. 새 저장소, 상주 worker, 웹 renderer나 권한 추정 큐는 없다. 실제 AppKit 할당과 전체 브라우저 RAM 변화는 측정하지 않았다.

## 현재 사이트 다운로드 설정 카드

2026-10-15 소스는 다운로드 패널 상단의 카드 하나, 라벨 7개와 버튼 하나를 고정 생성해 재사용한다. 현재 페이지 대상과 설정만 기억하며 모든 승인 사이트 목록이나 새 JSON, worker, 타이머, UI renderer는 추가하지 않는다. 현재 대상의 URL은 기존 8,192바이트 상한, origin은 2,048바이트 상한이며 표시용 문자열은 제한한다. 설정은 패널이 열린 경우만 읽고 재진입 조회는 생략한다. 같은 대상의 생략은 기존 카드와 포커스를 유지하며 대상이 바뀌면 무효화한다. 기존 권한 대기 4개 상한을 유지한다. 실제 CEF 조회 비용과 네이티브 메모리 변화는 측정하지 않았다.

## 방문 기록의 제한

2026-10-15 방문 기록 소스는 최근 30일, 1,000개 URL, JSON 2MiB로 저장을 제한한다. 파일 worker는 동시에 하나이며 대기 후보는 64개, URL과 제목 UTF-8 합계 256KiB다. 같은 URL의 연속 방문과 제목 변경은 대기 중 합친다. 새 방문이 상한을 넘으면 오래된 대기를 제외하고 안내를 남긴다. Store, 게시용 메타데이터 캐시와 작업 목록이 함께 있을 수 있어 2MiB가 프로세스 RAM 상한이라는 뜻은 아니다.

검색 결과는 전체 40행을 유지한다. 검색할 때 제한된 메타데이터만 읽으며 전체 소문자 캐시와 썸네일은 만들지 않는다. 네이티브 모드 전환과 삭제 확인 컨트롤 4개는 창당 고정 생성하며 별도 웹 UI renderer, 타이머나 상주 worker는 없다. 탭당 수집 작업 하나를 합쳐 게시한다. 임시 파일 테스트로 크기와 대기 상한을 확인했고 실제 AppKit 할당과 Chromium 전체 RAM, 장시간 방문 부하는 측정하지 않았다. [방문 기록 설계](history-design.md)를 함께 따른다.

## 네이티브 새 탭 화면

2026-10-13 시작 화면은 창당 고정 AppKit 컨트롤 한 세트와 현재 탭·공간·탐색 세대 대상 하나를 재사용한다. 실제 제출 중에만 같은 탭·공간의 중간 포커스 이동을 막는 대상 하나를 추가 보관하고, 성공·실패 모두 호출 반환 직후 해제한다. 탭에는 표시 자격 bool 하나가 추가된다. 탭별 입력 저장소·검색 요청·이미지 캐시·반복 타이머·새 UI renderer는 없다. 기존 빈 탭의 CEF 인스턴스는 유지하므로 그 Chromium 메모리를 없애는 변경은 아니다. 같은 조건의 RAM 비교는 미실행이며, [시작 화면 설계](start-page-design.md)와 [작업 기록](work-log.md)에서 실제 검증 수준을 구분한다.

## Aside 구성·토스 표현의 1차 UI

2026-10-13 사이드바와 주소줄 정리에서는 검색 배경·새 탭 배경·구분선용 고정 `SurfaceView` 세 개만 추가했다. 기존 탭 행·시스템 아이콘을 재사용하고 UI용 웹 renderer, worker, 반복 타이머, 영속 저장소를 추가하지 않았다. 색·간격·글자와 버튼 정렬은 AppKit에서 처리한다. 탭 수에 비례하는 새 컨트롤이나 이미지 캐시는 없으며, 이 설명은 소스의 자원 구조에 관한 것이다. 같은 조건의 RAM 전후 비교와 장시간 압박 검사는 아직 수행하지 않았다.

## 탐색 실패 복구의 상태

실패 안내는 기존 AppKit 창의 막대 하나와 재사용하는 두 버튼으로 표시한다. 복구 대상에는 현재 탭·공간·탐색 세대·실패 종류만 보관하며 본문·스크린샷·Browser/Frame 객체를 추가 보관하지 않는다. 선택과 실제 소속을 동작 직전에 다시 확인한다. UI용 renderer, 별도 worker·반복 타이머·영속 저장소는 추가하지 않았다.

같은 URL의 비사용자 후속 탐색이 시작되면 기존 오류 JSON 하나를 내부 후보로 이동한다. 문자열 전체를 별도 복제한 이력 목록을 만들지 않는다. 진행 중에는 공개 오류와 분리하고, 같은 URL의 후속 ABORTED에서만 복원하며 새 명시적 탐색·다른 오류·정상 commit·중지·렌더러 종료 등에서 폐기한다. 선택 진단은 원문 주소·오류 문자열 없이 코드·세대·일치 여부만 기록한다. 이는 추가 상태의 수명과 개수에 대한 설명이며 Chromium 전체 RAM 상한이나 메모리 절감 측정값은 아니다. 검증 수준은 [작업 기록](work-log.md)의 recovery-v1/v2를 따른다.

## 다운로드의 자원 제한

다운로드 대기, 저장창 선택, 전송, 취소 확인 대기를 합쳐 4개만 허용한다. 완료 기록까지 포함한 메타데이터는 24개다. 행마다 이름 256자, 출처 80자, 저장 경로 8,192바이트, 중단 사유 160자를 넘지 않는다. 원본 URL, 파일 내용, DownloadItem, 각 행의 Browser 객체는 보관하지 않는다. 전송 중 취소는 CEF가 최종 상태를 알려줄 때까지 자리를 유지한다. 재시도용으로 사용자가 승인한 원문 경로만 활성 콜백에 추가 보관하며 최대 4개×8,192바이트다. 엔진이 알려주는 진행 경로로 승인 경로를 대체하지 않고 종료 상태에서 해제한다.

목록이 열린 동안에만 행 스냅샷과 네이티브 행을 만들고, 닫을 때 행 UI를 해제한다. 닫힌 상태는 다운로드 진행, 저장 대기, 권한 대기 개수만 읽어 사이드바에 표시한다. 별도 worker, 반복 타이머, UI renderer, 다운로드 이력 DB를 추가하지 않았다. 이 상한은 Naru의 메타데이터 관리 범위다. Chromium의 임시 수신 버퍼, 실제 파일 크기, 브라우저 전체 RAM 상한이나 RSS 절감량을 뜻하지 않는다. v3의 실제 저장·취소·파일 선택·작업과 탭 수명을 확인했다. v4에서도 저장·취소·중단 처리를 확인했다. 아래 RSS 표본은 절감량을 뜻하지 않는다.

## 권한 v2 네이티브 검사 후 표본

2026-10-13에 다운로드 허용과 두 파일 저장, 사용자 요청 재개 검사를 마친 같은 v2 앱의 메인 PID 44130에서 RSS를 0.5초 간격 세 번 읽었다. 자체 작업을 정리한 원래 user 빈 탭 하나 상태이며 합계는 세 번 모두 722.094MiB였다. browser 258.141MiB, GPU 107.484MiB, network 87.688MiB, storage 70.609MiB, renderer 둘 108.453MiB와 89.719MiB다. 원본은 `artifacts/download-permission-v2-after-native-memory.json`이다.

공유 매핑을 중복 계산하는 RSS 합계이며 물리 RAM이나 메모리 절감량이 아니다. 여러 회귀와 실제 다운로드를 수행한 뒤의 표본이므로 이전의 새 앱 표본과 직접 비교하지 않는다. 탭 하나에서 renderer 둘이 관찰됐지만 이 표본만으로 누수나 추가 UI renderer를 판정하지 않는다.

## 다운로드 v4 측정과 정리

v4의 Rust 164개·CEF 회귀 32개와 재시작 검증 후 같은 바이너리의 RSS를 0.5초 간격 세 번 읽었다. 이전 CLI 스크린샷 경로는 base64 문자열과 디코딩된 PNG 전체 `Vec`를 동시에 보관했다. 현재 CLI는 디코딩 결과를 파일에 직접 쓴다. 32MiB의 base64가 반환되는 경우 약 24MiB의 별도 이미지 버퍼를 만들지 않게 된다. 이는 코드 경로에서 제거한 할당량이며 앱 전체 RSS가 그만큼 줄었다는 측정 결과는 아니다. 공간 미리보기는 파일을 쓰지 않고 크기가 제한된 PNG를 메모리에서 디코딩한다.

캡처 자리는 CLI 요청과 별도로 관리한다. 시간 초과, handoff, 렌더러 종료 알림으로 응답 대기가 끝나도 Chromium의 네이티브 캡처가 끝났다고 간주하지 않는다. 시작 단계에서 CEF가 실행을 거절하면 즉시 반환한다. 실행을 수락한 뒤에는 실제 캡처 결과, DevTools 연결 종료 또는 탭 닫힘 콜백에서 반환한다. 렌더러 종료 알림만으로는 자리를 반환하지 않는다. CLI PNG 저장은 기존 파일을 덮어쓰지 않으며 디코딩 실패로 생긴 부분 파일은 파일 종류와 inode가 일치할 때만 정리한다.

팝업은 생성 요청 때 자리를 예약하고 생성 완료, 취소, opener 종료에서 해제한다. 작업의 제어권이 바뀐 뒤 늦게 생성된 탭은 조작 대상에서 제외하고 정상 종료를 요청한다. 사용자가 연 DevTools 창에는 opener의 이미 사용한 예약을 상속하지 않는다.

active 작업의 새 탭 링크도 UI 큐에 넣기 전에 생성 자리를 예약한다. 큐 실행과 생성 콜백에서 opener 존재·소유권·상태·revision을 다시 검사하고 거절·취소·실패 시 자리를 반환한다. 작업 소속이 없는 탭이나 paused 작업의 탭에서 여는 사용자 링크는 이 자동화 생성 예산을 사용하지 않는다. 백그라운드 링크는 선택을 유지하지만 페이지 메모리를 별도로 제한하거나 폐기하지는 않는다.

`status`의 `resources`에는 `automationTabLimit`, `taskTabLimit`, `pendingTabCreations`, `captureLimit`, `capturesInFlight`가 포함된다. 전체 탭 한도에서는 `TAB_LIMIT`, 작업 한도에서는 `TASK_TAB_LIMIT`을 반환한다. 두 조건에 동시에 걸리면 검사 경로에 따라 둘 중 하나가 먼저 반환될 수 있다. 이 오류 때문에 사용자 탭을 자동으로 닫아서는 안 된다.

## 세로 탭 행의 AppKit 재사용

2026-10-13 탭 행 개선은 `src/control_panel.rs`에서 현재 공간의 행만 보관하고, 탭 ID와 공간이 모두 같으면 선택 버튼·닫기 버튼·아이콘 뷰·제목 필드를 재사용한다. 제목·URL·로딩·선택 상태 갱신 때 해당 컨트롤의 값과 배치만 바꾸며, 제거되거나 공간이 바뀐 행은 뷰에서 떼고 보유 참조를 해제한다. 다른 공간의 전체 행을 별도 캐시에 쌓지 않는다. 변경 서명, 현재 탭 목록과 갱신 중의 임시 벡터·맵은 계속 사용하며, 행별 닫기 버튼을 포함한 네이티브 UI 비용은 표시 탭 수에 비례한다. 탭 행 가상화나 Chromium 페이지 메모리 회수 기능은 추가하지 않았다.

접힌 사이드바의 76포인트 폭은 선택과 닫기 영역을 나누기 위한 배치다. 새 웹 renderer, 별도 프로세스나 반복 polling 타이머는 추가하지 않았다. 같은 ID라도 공간이 바뀐 행은 재사용하지 않고, 닫기 직전 실제 소속을 다시 확인한다. 주소 초안 보존용 `SidebarAddressHandoff`는 배경 행 닫기 호출 동안 현재 탭·공간·URL·세대를 담은 한 개의 임시 값이며 호출 뒤 해제한다. 예외는 같은 문서의 제어권 인계로 세대가 정확히 한 번 증가한 경우에만 적용한다.

Rust 178개와 전체 타깃 검사·format·release 빌드가 통과했다. 같은 바이너리의 빈 탭에서 행별 닫기, 접힌 배치와 주소 초안·입력 포커스 보존을 확인했다. 사용자 승인 후 같은 tab-rows-v1 바이너리의 로컬 HTTP 완료, 배경 행 닫기의 이탈 확인 취소/확정과 기존 CEF 회귀 32개를 확인했다. 정리 뒤 원래 user 빈 탭 1만 남고 다운로드·권한·저장·wait·캡처·탭 생성 대기는 모두 0개였으며, 네이티브 ⌘Q로 앱의 exit 0을 확인했다. 근거는 `artifacts/tab-rows-v1-approved-native.json`과 `artifacts/tab-rows-v1-suite-state.json`이다. 자원 예약 반환과 정상 종료를 메모리 회수량 측정으로 해석하지 않는다. 이 절은 컨트롤의 수명과 재사용 경로를 설명한다. AppKit 할당 횟수, 최대 탭 수 부하, RSS와 physical footprint를 같은 조건에서 비교한 측정은 아직 없으므로 메모리 절감량이나 절감률을 제시하지 않는다. 기존 다운로드 권한 v2의 RSS 표본은 이 변경의 측정값으로 사용하지 않는다.

## 새 탭 검색 최종 빌드의 자원 검증 범위

검색 표시 별칭을 반영한 tab-search-label-v1 release 앱의 SHA-256은 `9a24e9181f909c07482cf26f610676be39b3b618990525b37d65faab3ac6eb88`다. 같은 소스의 Rust 179개·전체 타깃 검사·format·diff 통과 뒤 release 빌드가 exit 0으로 끝났다. 기존 탭 행 v1 앱을 정상 종료한 뒤 최종 검색 앱의 최초 실행 PID는 68589였으며 사용자 프로필을 유지했다. 빌드 중간 파일 1,263개·671.5MiB를 정리했으며 이는 디스크 정리량이다.

새 검색은 일반 제목을 추가 복사하지 않고 고정된 “새 탭” 별칭을 참조하며 기존 검색 상한을 유지한다. 실제 검색창에 “새”와 “새 탭”을 붙여넣어 원래 사용자 빈 탭 하나가 결과로 표시되고 Return으로 선택되는 동작을 확인했다. IME 검사는 아니며 AppKit 할당이나 RSS를 새로 측정하지 않았다. 첫 HTTP의 commit 전 WAIT_TIMEOUT은 `artifacts/tab-search-label-v1-validation.json`에 보존했다. 사용자 승인 후 같은 최종 바이너리에서 HTTP·네이티브 이탈 확인·CEF 회귀 32개가 통과했다. 회귀 뒤 검사 작업 9개가 모두 finished였으며 원래 user 빈 탭 1과 다운로드·권한·저장·wait·캡처·탭 생성 대기 0개를 확인했다. 근거는 `artifacts/tab-search-label-v1-approved-native.json`, `artifacts/tab-search-label-v1-suite-state.json`, `artifacts/tab-search-label-v1-post-suite-state.json`이다.

네이티브 ⌘Q의 exit 0 뒤 같은 SHA와 프로필로 재시작한 PID 71159에서 추가 승인 질문 없이 HTTP가 완료됐고 SecurityAgent는 관찰되지 않았다. 자체 HTTP 탭을 닫고 fixture를 정상 종료한 뒤 원래 user 빈 탭 1만 선택됐으며 작업 목록과 모든 대기는 0개였다. 최신 앱 하나와 사용자 프로필을 유지했고 이번 승인 후 검증에서는 재빌드하지 않았다. 당시 디스크 사용량은 target 약 2.9MiB, dist 약 335MiB, 검증 자료 약 15MiB, CEF 캐시 약 339MiB다. 근거는 `artifacts/tab-search-label-v1-restart-http.json`, `artifacts/tab-search-label-v1-final-state.json`, `artifacts/tab-search-label-v1-final-validation.json`이다. 예약 반환·정상 종료·디스크 정리 수치는 RAM 절감량이 아니다. 동일 바이너리의 재시작만 확인했으며 실제 인증서 서명과 변경 빌드 사이 키체인 권한 유지는 검증하지 않았다. 이전 tab-rows-v1 결과도 위의 별도 바이너리 증거로 유지한다.

## 관찰과 브라우저 UI

열린 Shadow DOM 지원은 페이지 관찰 범위를 넓힌다. 순회 상한에 도달하면 `read.page.truncated`의 `nodes`, `shadowRoots`, `depth`로 알리고, 출력 상한은 기존 `text`, `interactive`로 구분한다. 후속 소스는 접근 가능한 iframe 16개 슬롯, 중첩 8단계에서 기존 read 예산을 공유하며 `frames`, `frameDepth` 잘림을 추가한다. 문서별 isolated context가 지연 생성될 수 있어 이 상한을 contentDocument 조회 전에 적용한다. 닫힌 Shadow DOM, 접근 불가능한 iframe 내부, 캔버스 내부는 수집하지 않는다. 이 제한은 관찰용 작업과 응답 크기를 줄이는 장치다. 이미 로드된 페이지 DOM, JavaScript heap, 이미지, renderer 프로세스의 메모리를 줄이거나 10,000노드로 만드는 기능은 아니다.

`src/control_panel.rs`는 NSWindow 하나 안의 접는 세로 탭, 공간 카드, 탐색 막대, 상태 표시와 중지 버튼을 AppKit 컨트롤로 구성한다. CEF Alloy 페이지 뷰를 같은 콘텐츠 영역에 붙이며 별도 작업 제어 창이나 UI용 웹 renderer는 추가하지 않는다. `src/spaces.rs`는 탭 ID와 선택, 빌린 탭의 복귀 위치를 보관하며 빈 작업 공간 생성은 CEF 탭을 만들지 않는다. 공간들이 같은 프로필을 공유하므로 공간 수를 프로필이나 renderer 프로세스 수와 같다고 볼 수 없다.

2026-10-11 UI 정리에서는 고정된 SF Symbols 종류를 공유 캐시에 보관한다. 탭 수나 작업 수에 비례해 아이콘 종류를 계속 추가하지 않는다. 카드 미리보기는 기존 NSImage와 마스크 영역의 배치로 비율을 유지해 채우며, 크기에 맞춘 별도 래스터 이미지를 생성하지 않는다. 배경·상태 배지·글꼴·여백 변경에 새 웹 renderer나 반복 타이머를 추가하지 않았다. 이는 구현 경로의 설명이며 앱 전체 메모리 절감 측정값은 아니다.

공간을 전환할 때 다른 공간의 페이지 뷰는 숨기지만 Chromium 페이지 자체를 자동 폐기하지 않는다. 작업 범위의 새 탭도 현재 화면을 바꾸지 않을 뿐 페이지 메모리는 사용한다. 작업 소유권과 표시 공간이 달라도 같은 CEF browser ID이며 생성 예산의 단위는 변하지 않는다. 변경 알림을 한 번의 지연 작업으로 모으며 반복 타이머로 상태를 읽지 않는다. 세로 탭이나 공간 분리 자체로 앱 전체 RSS 절감량을 계산할 수는 없다.

공간 목록을 열면 현재 페이지에 보이는 최대 8개 카드의 대표 탭을 순차 캡처한다. `about:blank`는 캡처하지 않고 새 탭 안내를 표시한다. CEF clip은 최대 240×150 포인트를 목표로 축소 요청하며 Retina 화면의 실제 결과 크기는 별도 실행 검증이 필요하다. UI는 PNG 헤더의 크기가 640×480 픽셀 이하이고 파일 데이터가 1MiB 이하일 때만 디코딩한다. 현재 카드의 NSImage 참조만 보관하며 별도 디스크 캐시는 만들지 않는다. overview를 닫으면 카드와 이미지 참조를 해제한다. 닫힌 뒤 도착하거나 탭과 탐색 세대가 바뀐 결과는 표시하지 않는다.

CLI screenshot과 미리보기는 `captures`의 자리 하나를 공유한다. 미리보기 때문에 진행 중인 캡처가 있을 때 CLI screenshot은 `CAPTURE_BUSY`를 반환할 수 있다. 미리보기 결과와 JSON을 처리하는 일시적인 버퍼, 디코딩한 이미지, Chromium 캡처 버퍼는 서로 구분해야 한다. PNG 바이트 상한을 전체 메모리 상한으로 해석하지 않는다.

렌더러가 종료되면 해당 탭의 pending 요청과 wait를 정리한다. 네이티브 캡처 자리는 실제 결과, DevTools 연결 종료 또는 탭 닫힘에서 반환한다. 탭과 작업 기록은 유지하고 자동 재시도도 하지 않는다. 이 처리는 실패한 요청의 수명 관리를 위한 것이며 메모리 회수를 목적으로 사용자 탭을 폐기하는 기능이 아니다. 복구는 명시적인 탐색 후 새 문서 commit을 확인하는 경로를 따른다.

## 측정

실행 중인 앱의 정확한 메인 PID를 지정한다. 측정 스크립트는 앱을 실행하거나 종료하지 않으며 별도 상주 프로세스도 만들지 않는다.

```bash
python3 scripts/measure-memory.py --pid <앱_PID> --samples 3 --interval 1 \
  --footprint --output artifacts/memory-new-run.json
```

기존 출력 파일은 덮어쓰지 않는다. 표본 수는 1~10개, 간격은 0.1~5초다. 지정 PID와 PPID로 이어지는 자손만 포함하며 시작 시각을 비교해 메인 PID 재사용과 종료를 감지한다. 결과에는 URL, 프로필 경로, 전체 프로세스 인자를 기록하지 않는다.

- `rssMiB`: 각 프로세스의 RSS. `ps`의 KiB 값을 MiB로 환산한다.
- `rssSumMiB`: 한 표본에 포함된 RSS의 합계. 공유 매핑이 중복되므로 고유 RAM 사용량이 아니다.
- `peakObservedRssSumMiB`: 수집한 표본 합계 중 최댓값. 표본 사이의 실제 최고점을 보장하지 않는다.
- `physicalFootprintMiB`: 선택적으로 `vmmap -summary`에서 읽은 현재 값. 경고, 실패 또는 대상 변경 시 `null`과 사유를 기록한다.
- `footprintSumMiB`: 마지막 RSS 표본의 모든 프로세스를 성공적으로 측정한 경우에만 계산한다. 순차 측정이므로 같은 순간의 값은 아니다. 프로세스별 최고점을 합하지 않는다.

footprint 측정은 PID당 최대 8초, 측정 창 30초이며 프로세스 동일성 조회는 회당 최대 5초다. 모든 항목을 측정하지 못하면 합계도 `null`이다.

## 북마크와 통합 검색의 자원 경계

`src/bookmark_runtime.rs`는 완료된 Store의 메타데이터를 `Arc<[Bookmark]>`로 보관한다. 파일을 읽거나 변경할 때 worker를 하나만 만들고, UI는 캐시에서 검색 결과를 가져온다. 저장 완료 때 캐시를 교체하며 UI 이벤트마다 전체 목록을 복제하지 않는다. 정상 종료는 진행 중인 파일 작업이 끝날 때까지 기다린다. 새 DB 프로세스, 파일 감시 프로세스, 반복 polling과 UI용 웹 renderer는 추가하지 않았다.

검색·미리보기 v2는 열린 탭과 북마크를 합해 최대 40행을 표시한다. 기존 북마크 검색의 최대 30행을 사용하고 탭을 먼저 표시한다. 검색 인덱스나 별도 전체 목록 캐시를 추가하지 않았다. 사용자 승인 후 네이티브 화면에서 같은 숫자 ID인 탭과 북마크를 구분해 선택했고 키보드·마우스, 사용자 탭 재사용·새 탭 생성과 AI 작업 상태 보존을 확인했다. 최대 항목 수의 UI 부하나 메모리를 측정한 결과는 아니다. 근거는 `artifacts/search-preview-v2-native.json`이다.

v2의 미리보기 시작 보호는 DevTools observer가 등록되고 현재 문서와 메인 로딩이 완료됐을 때만 새 캡처를 요청한다. CEF 로딩 여부를 상태 borrow 밖에서 확인하고, 예약 전에 탐색 세대와 공간을 다시 검사한다. 미준비 후보는 캡처 자리나 시도 기록을 소비하지 않는다. 실행 중인 캡처의 반환 조건은 바꾸지 않았다. `artifacts/search-preview-v2-delays.json`에서 빠른 문서는 파란 미리보기를 표시했고, 응답 헤더 대기와 DOM interactive 상태의 이미지 로딩 중인 문서는 안내 화면을 유지했다. 각 대기를 POST로 해제하자 공간 목록을 다시 열지 않아도 주황 문서, 초록 문서와 SVG가 차례로 표시됐다. 과거 승인 대기 중 캡처가 남은 현상의 원인을 확정하거나 복구했다고 주장하지 않는다.

검증한 v2 바이너리 SHA-256은 `f9168ced388db274d3d18538a792081c7b5302bffc6b7817b4a59616c9227f74`다. `artifacts/search-preview-v2-build.log`에서 release 빌드와 중간 파일 1,263개·669.4MiB 정리를 확인했다. 이는 디스크 정리량이며 RAM 절감량이 아니다. 승인 전 첫 탐색의 5초 `WAIT_TIMEOUT` 이후 사용자 승인 후 같은 앱에서 로컬 CEF 22개를 통과했다. 검증용 작업·탭·북마크를 정리하고 기존 사용자 탭을 보존했으며 캡처·생성 예약은 0이었다. 근거는 `artifacts/search-preview-v2-suite.json`과 `artifacts/search-preview-v2-suite-state.json`이다. v2 앱은 exit 0으로 종료했다. v2의 새 RSS 측정은 없으며 아래 v1과 v6 측정은 별도 기록이다.

v2에서는 검색 중 기억된 현재 탭을 닫으면 입력 포커스를 잃는 결함이 재현됐다. 제거하는 CEF 뷰 안에 실제 first responder가 있는 경우만 해제하는 v3 수정은 Rust 128개와 전체 타깃 검사를 통과했다. 최초 샌드박스 실행의 소켓 bind 권한 오류 3건은 `artifacts/search-preview-v3-rust-tests-sandbox.log`, 재실행 성공은 `artifacts/search-preview-v3-rust-tests.log`, 전체 타깃 검사는 `artifacts/search-preview-v3-check.log`에 기록했다.

당시 `dist`와 실행 앱은 검색·미리보기 v3(`93bbf74352f3565713a24b4c9b20729e2b7bb627f8b771c7f91f35ebb9b9a9bd`)다. `artifacts/search-preview-v3-build.log`에 release 빌드와 중간 파일 4,332개·2.4GiB 정리를 기록했다. 이 역시 RAM 절감량이 아니다. 첫 HTTP 탐색은 5초 `WAIT_TIMEOUT`이었지만 사용자가 키체인을 항상 허용한 뒤 같은 바이너리의 로딩 완료를 확인했다. 이번 대기는 해소됐으며 재서명 후 승인 요청을 없앤 결과는 아니다.

`artifacts/search-preview-v3-native.json`에서 빈 탭과 HTTP 탭을 닫은 뒤 통합 검색의 필드 포커스와 추가 붙여넣기를 유지했다. 북마크를 새 사용자 탭으로 열 때 AI 작업의 active·revision 1·선택 탭 5를 보존했다. 북마크 편집 중 원래 탭을 닫아도 이름 입력의 포커스와 고정 URL을 유지했고 실제 파일에 이름을 저장했다. 검증 북마크 삭제 후 본문은 `items: []`, `nextId: 5`이며 검증 AI 작업도 종료했다.

## 단일 창 전환의 회귀 검증

```bash
python3 tests/single_window_smoke.py --data-dir "$LIGHT_BROWSER_DATA_DIR" \
  --output-dir artifacts/single-window
```

이미 실행 중인 앱을 대상으로 하며 기존 탭 1~5개를 보존한 채 두 작업의 탭을 만든다. 현재 테스트는 생성 후 명시적으로 공간을 전환한 뒤 CLI의 `windowMode`, `activeTab`, 각 탭의 `active` 일치, 배경 탭의 읽기와 PNG, finish 이후 다른 탭 보존을 검사한다. 생성 예약과 캡처 자리의 최종 반환도 확인한다. 합성 DOM 클릭을 실제 사용자 입력으로 간주하지 않으며 새 탭 링크의 생성과 opener 소유권은 별도 네이티브 UI 검사로 분리한다. 기존 탭 수가 조건을 벗어나면 사용자 탭을 닫지 않고 실패한다. 다른 CLI 테스트와 동시에 실행하지 않는다.

공간 분리 이전인 2026-10-10의 `artifacts/single-window-v2-validation.json`은 실제 CEF를 사용한 로컬 HTTP 회귀 7개 묶음, 44개 항목 통과를 기록한다. 그중 단일 창 6항목은 배경 A 캡처가 같은 실행의 전경 A와 일치하고 전경 B와 구별되는지, 마지막 생성 예약과 진행 중 캡처가 0인지 확인했다. 새 탭 링크의 생성과 opener 소유권, 작업 중지, 마지막 탭 종료는 같은 바이너리의 `artifacts/single-window-v2-native.json`에 따로 기록했다. 이 기록은 새 공간 UI의 검증이 아니다.

생성 예약과 캡처 0은 Chromium이 페이지 메모리를 모두 반환했다는 뜻이 아니다. 동작 검증과 위의 메모리 표본을 구분하며, 더 많은 시나리오의 조건은 [아키텍처 문서](architecture.md)의 검증 표에서 확인한다.

새 공간 테스트는 기존 탭 1~4개를 보존하면서 빈 작업 공간, 배경 생성의 선택 보존, 공간별 선택, 종료 결과와 borrowed 탭 복귀, 마지막 생성 예약과 캡처 자리의 반환을 검사한다. 네이티브 UI의 표시 결과와 코드에서 확인한 이미지 참조 해제·늦은 결과 처리는 검증 수준을 구분한다. 최종 바이너리의 공간 검사 10항목과 기존 회귀 44항목이 통과했다. 네이티브 화면에서 실제 미리보기 3개와 배경 탐색 후 이미지 갱신을 확인했다. 늦은 결과 처리와 크기 상한은 코드·단위 검사로 확인했으며, 미리보기 PNG의 실제 픽셀 치수, 디코딩 할당량, 8개 카드 페이지 부하는 직접 측정하지 않았다. 근거는 `artifacts/spaces-v3-validation.json`과 `artifacts/spaces-v3-native.json`이다.

## 추가 경량화의 판단 기준

다음 최적화는 같은 프로필·페이지·창 수·대기 시간에서 브라우저, renderer, GPU, network, storage를 함께 측정한 뒤 진행한다. 시작 직후, 동일 페이지를 읽고 캡처한 뒤, 작업 종료 뒤의 값을 구분한다. 샌드박스와 프로세스 격리, 기본 웹 기능을 유지한 상태에서 비교한다.

자동 freeze나 탭 폐기는 아직 없다. freeze를 RAM 해제로 간주하지 않으며, 폐기로 인한 입력 내용과 작업 상태의 손실을 먼저 설계해야 한다. 사용자 소유 탭과 borrowed·keep 탭을 자동 폐기하지 않는다. CEF/Chromium 자체의 메모리 상한도 구현하지 않았다.
