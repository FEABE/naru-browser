# 공간 안에서 탭 순서 바꾸기

2026-10-15 소스 구현이다. 보기 메뉴의 **현재 탭 위로 이동**과 **현재 탭 아래로 이동**으로 선택한 탭을 같은 공간의 이웃과 한 칸 바꾼다. 첫 탭의 위, 마지막 탭의 아래는 비활성화하며 끝에서 반대편으로 순환하지 않는다. 후속 드래그 정렬은 아래 계약으로 같은 공간에서 보이는 위치로 이동한다. 사용자 공간과 AI 공간에서 같은 표시 순서를 사용한다.

선택한 페이지, 탐색 세대, 주소와 시작 화면 입력, 페이지 찾기, AI 작업의 소유권과 revision을 직접 변경하지 않는다. 탭을 고르거나 페이지에 입력하는 동작과 구분한다. 실제 입력 포커스와 AppKit 메뉴 동작의 실행 검증은 남아 있다.

## 표시 순서와 수명

`spaces::Space`는 기존 탭 소속 맵과 별도로 `Vec<i32>`에 표시 순서만 보관한다. 새 탭은 해당 공간의 마지막에 추가되고 같은 공간에 이미 있는 탭을 다시 등록해도 중복되거나 끝으로 이동하지 않는다. 다른 공간으로 입양되거나 반환된 탭은 목적지 마지막에 놓인다. 원래 위치를 복원하는 기능은 없다. 현재 탭이 닫히면 해당 공간의 표시 순서상 첫 탭을 고른다. 이전에는 가장 낮은 탭 ID를 골랐다.

`SpaceView.tabs`와 `browser::shell_snapshot`이 같은 순서를 전달한다. 사이드바, 번호 선택, 이전·다음 탭 순환이 이 순서를 사용한다. CLI의 `spaces`에 포함되는 탭 목록도 표시 순서이고, 기존 `tabs`와 task 소유권 목록의 ID 및 제어 계약은 바꾸지 않는다.

순서는 이번 실행 중에만 유지한다. 저장 파일, 탭 복원, CLI 순서 변경 명령과 공간 간 드래그 이동은 추가하지 않았다. 재시작 탭 복원은 사용자 보류 상태를 유지한다.

## 메뉴와 검증

`ShellTarget.menuWillOpen`이 탭 ID, 공간, 인접 탭 ID와 방향을 메뉴 항목마다 고정한다. 뒤이은 validation과 실행은 같은 메뉴 항목과 대상을 확인하고 새 선택으로 자동 바꾸지 않는다. 현재 창이 활성 상태이고 공간 보기나 전체 패널이 닫혀 있어야 하며, 입력기 조합 중에는 실행하지 않는다.

`control_panel::reorder_tab → browser::reorder_tab_from_sidebar → spaces::reorder_adjacent`가 실제 선택, 공간 소속, 탭 수명과 방향별 이웃을 다시 검사한다. 검증과 순서 교체 사이에 CEF나 AppKit을 호출하지 않는다. 메뉴가 열린 동안 탭이 닫히거나 입양·반환되고, 선택 또는 이웃 방향이 달라지면 거절한다. 정상 문서 탐색이나 AI 상태 변화만으로 표시 순서를 임의로 초기화하지 않는다.

성공 뒤 기존 지연 UI 갱신을 요청한다. 선택한 탭의 기존 행 컨트롤을 재사용하고 이동한 위치를 보이게 한다. 선택 변경이나 강제 페이지 포커스, AI 인계를 직접 요청하지 않는다. 갱신은 기존 `sync → apply_selection(false)` 경로를 거친다.

## 사이드바 드래그 정렬

선택 버튼에 붙인 `NSGestureRecognizer`의 하위 클래스가 마우스 시작 위치에서 6pt 이상 움직였을 때만 드래그를 시작한다. 그보다 작은 이동은 `Possible` 상태를 유지하고 버튼을 놓을 때 `Failed`로 전환한다. 지연된 원래 이벤트를 AppKit이 버튼에 전달하므로 별도 클릭을 합성하지 않는다. 닫기 버튼에는 제스처를 붙이지 않는다. 기존 메뉴와 키보드 조작은 유지한다.

시작 시 탭 ID, 공간, 선택과 현재 표시 순서의 ID 목록 하나를 고정한다. 드래그 도중 목록을 복제하지 않으며 `Rc`로 같은 대상을 참조한다. 실제 행 좌표에서 원본 행을 제외한 삽입 위치를 찾고 선 하나로 표시한다. 끝에서만 `browser::reorder_tab_by_drag → spaces::reorder_before`로 순서를 바꾼다. `Vec` 안의 구간을 회전하며 선택한 탭과 브라우저 문서, 작업 제어권은 변경하지 않는다. 배경 탭도 페이지를 선택하지 않고 이동한다.

현재 공간, 선택, 전체 탭 순서와 생존 상태가 시작 시점과 같아야 한다. 네이티브 창과 행, 제스처 객체, 배치와 입력기 조합을 조회한 뒤에도 대상을 다시 확인한다. 목록 변경이나 공간 전환, 전체 패널, 창 비활성화와 종료는 진행 중 이동을 취소한다. Escape는 제스처의 `keyDown` 전달을 가정하지 않고 기존 앱의 키 이벤트 처리에서 소비한다. 취소 후 늦게 오는 변경과 종료 이벤트로 이동을 다시 시작하지 않는다.

현재 구현은 드래그를 시작한 스크롤 영역을 고정한다. 영역을 벗어나거나 휠과 배치 변경으로 표시 영역이 달라지면 취소한다. 가장자리 자동 스크롤과 화면 밖 위치까지 이어지는 드래그는 남은 작업이다. 긴 목록에서는 먼저 스크롤한 뒤 보이는 행을 옮기거나 기존 위아래 이동 메뉴를 사용할 수 있다. 공간 간 이동과 외부 파일, 주소 드롭은 받지 않는다.

Apple SDK의 `NSGestureRecognizer.h`에서 이벤트 지연과 subclass 이벤트 전달, 종료 상태의 action 계약을 확인했다. 분리된 AppKit 검사에서는 기본 `NSPanGestureRecognizer`가 1pt 이동도 드래그로 처리해 클릭을 소모하는 사례를 관찰했다. 직접 subclass로 이동 거리를 검사하는 방식은 작은 이동을 클릭으로 남겼다. 기본 `locationInView`가 원점을 반환한 검사 결과에 따라 이벤트의 window 좌표를 보관하고 현재 문서 좌표로 변환한다. 이 검사는 자체 창에 게시한 합성 이벤트를 사용하며 실제 마우스 입력이나 최종 Naru의 CEF 통합 증거는 아니다. 실행별 실패와 수정 결과는 작업 기록에 구분한다.

## 자원과 검증 경계

공간당 Vec 하나와 탭 ID 배열, 메뉴 대상 최대 두 개를 추가한다. 탭이 모두 없어지면 배열을 해제한다. capacity가 32를 넘고 길이가 capacity의 1/4 이하가 됐을 때만 현재 길이의 두 배를 기준으로 축소 요청해 삭제마다 재할당하지 않는다. 실제 allocator와 앱 전체 RAM의 상한·절감량을 보장하는 값은 아니다.

드래그는 재사용하는 탭 행마다 제스처 객체 하나, 창마다 삽입선 하나를 추가한다. 진행 중인 제스처 하나만 탭 수에 비례하는 `i32` 순서 목록과 고정된 네이티브 참조를 보관한다. 목록 요소의 크기는 탭당 4바이트지만 Vec 용량, 참조 대상과 AppKit 할당 비용은 별도다. 취소와 종료 때 세션을 해제하며 페이지 캡처나 드래그용 이미지는 생성하지 않는다.

새 worker, 타이머, 웹 renderer, 이미지 캐시와 저장소는 없다. 순수 상태와 비활성 CEF handle 기반 단위 검사, 전체 타깃 컴파일 결과는 [작업 기록](work-log.md)에 남긴다. 실제 메뉴 활성화, 주소 편집과 IME, 사이드바 스크롤과 접근성 순서, 배경 CLI 변경과 동시 드래그, 최종 앱의 장시간 사용과 RAM은 별도 실행 검증이 필요하다.

최종 tab-drag-v2는 Rust 단위 282개와 기본 구성, CLI 전용 구성의 전체 타깃 컴파일 검사, format을 통과했다. 신규 9개는 모델 순서와 무변경, 배경 탭의 선택과 AI 상태 보존, 오래된 대상 거절, 위치 계산과 6pt 경계를 확인한다. 최초 컴파일의 NSButton과 NSView 포인터 타입 불일치는 명시적으로 상위 view 참조를 사용하도록 수정했다. `artifacts/tab-drag-v2-check.json`과 검사 로그가 근거다.

분리된 AppKit 검사에서 클릭, 드래그, 드래그 뒤 클릭, 작은 흔들림, 작은 이동 뒤 드래그 5개가 통과했다. 추가 Escape 검사는 게시한 합성 키 이벤트가 애플리케이션에 전달되지 않아 검증할 수 없었다. 테스트 앱을 활성화해도 같았으므로 제스처나 제품의 취소 결함으로 단정하지 않는다. 초기 검사 실패와 원인 해석 정정은 `artifacts/tab-drag-native-probe/summary-v4-v5.json`에 보존했다. 최종 Naru의 실제 Escape와 입력기, 주소 초안, CEF 화면은 여전히 실행 검증 전이다.
